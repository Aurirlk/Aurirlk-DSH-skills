# 连接池耗尽：取证与根除

```
CannotGetJdbcConnectionException
  total=20  active=20  idle=0
```

看到这三个数，**第一反应不该是"数据库挂了"**。

`active = total` 且 `idle = 0` 的意思是：**池里的连接全被应用程序借走了，一个都没还**。数据库可能好好的，是应用自己不肯松手。

判断错了，后面全错：去查 DB 慢查询、去加索引、去联系运维 —— 而真正的瓶颈在你自己的代码里。

## 一、先分清四种耗尽

| 形态 | 池指标 | 真实原因 | 处置方向 |
|---|---|---|---|
| **借空不收** | `active=total, idle=0`，且长时间不回落 | 泄漏 / 长事务 / 死循环持连接 | 找持有者，见第二节 |
| **并发超限** | `active≈total` 但会周期回落 | 瞬时并发 > 池容量 | 限流 + 池容量规划 |
| **等连接的僵尸** | `active=total`，线程大量 WAITING | 超时了但任务没被取消 | 取消语义 + 闸门 |
| **DB 侧拒绝** | `active` 上不去，`idle>0`，连接建立失败 | 网络 / `max_connections` / 认证 | 这是真·DB 问题 |

**区分"借空"和"DB 拒绝"只看一个指标**：`idle` 是否接近 `total`。idle 还有留存，说明应用没借满，问题在建立连接那一侧。

## 二、谁在占连接

按出现频率排：

### 1. 无上限的并行

线程池/虚拟线程"来多少开多少"，每个任务各要一条连接。**虚拟线程尤其危险** —— 它让"开十万个"变得没有成本感，但连接池还是 20。

### 2. 超时不取消任务的僵尸

```java
CompletableFuture.supplyAsync(this::query)
    .orTimeout(3, TimeUnit.SECONDS)   // ← 只是让等待方超时
```

`orTimeout` **不会取消底层任务**。等待方早就返回 504 了，底层仍在排队等连接、拿到后继续跑。并发一高，这些僵尸把池子占满，而监控上看不到对应请求（请求已经结束了）。

**这是最隐蔽的一类：日志里没有报错，只有"越来越慢"。**

### 3. 后台批处理与在线流量共用一个池

文档解析、向量化、报表计算这类后台任务，往往是固定线程数（8 个），看起来不多。但它们跑得久（每条几十秒到几分钟），和前台检索抢同一个池 → 前台开始超时。

### 4. 长事务 / 忘记提交

`@Transactional` 包住了一次外部 HTTP 调用或一次模型 embedding 请求 —— 整个外部调用期间连接一直被占着。

## 三、不要照抄通用模板

处置方案通常是别处看来的。**先在本仓验证它的三个假设**，否则改完更糟：

| 模板假设 | 怎么验 | 不成立时的后果 |
|---|---|---|
| 「用 `@Transactional` 包住了 embedding」 | grep 该方法有无注解、有无 `TransactionTemplate` | 改事务边界完全无效 |
| 「用 MyBatis `Cursor` 流式读」 | grep `Cursor` / `selectCursor` 是否真存在 | 改成不存在的 API，编译不过或走了别的分支 |
| 「pool 名是 `omadminadminai`」 | 读 yml 里的 `pool-name` | 监控/日志筛选全落空，看不到真实指标 |
| 「池大小是配置项」 | 看是不是硬编码数字、有没有 `${...}` | **环境变量改不动它**，见第六节 |

**这条可以推广**：任何来自外部的修复方案，先在代码里定位它假设的那几行。定位不到就说明方案不是为你这个代码库写的。

## 四、限流挂在哪里

**挂在唯一汇入口，不要挂在各个入口点。**

反例：HTTP Controller 加一道、Tool 调用加一道、Agent 调用加一道、定时任务再加一道 —— 四处各写一份，漏一处就等于没有，而且阈值不一致。

正例：所有这些路径最终都调同一个服务方法

```java
public RagResult search(SearchRequest req, RagConfigDO cfg) {
    if (!gate.tryAcquire()) {
        return RagResult.degraded("busy");   // 降级，不排队
    }
    try { ... } finally { gate.release(); }
}
```

### 两个语义决定

1. **抢不到就降级，不排队。**
   排队会让请求堆在池前面，用户等到 30 秒超时，体验比"立刻告诉你忙"差得多，还占线程。

2. **闸门是信号量，不是池。**
   池管"物理连接"，闸门管"同时在跑多少个业务动作"。两个数量级不同（比如池 20、闸门 8），闸门先拦，池就永远不会被借空。

后台任务单独限：并发默认压到 2，再加一个总开关（业务不需要时可以整块关掉）。

## 五、三个配置陷阱

### 1. `leak-detection-threshold` 必须 ≥ `connection-timeout`

泄漏检测的原理是"借出超过 N 毫秒就警告"。如果 N 小于连接超时时间，那么**每一次正常的慢查询都会报泄漏** —— 满屏警告，真实的泄漏反而被淹没。

```
connection-timeout: 30000
leak-detection-threshold: 30000   # 或 0（关闭）
```

设成 10000 + 超时 30000 = 全是误报。

### 2. 扩 `maximum-pool-size` 不是根治

池调大只是把压力推给数据库的 `max_connections`。20 → 50 之后：

- 每个连接都吃 DB 内存和文件句柄
- 50 个并发慢查询，DB 侧更容易雪崩
- **真正的泄漏或僵尸还在，只是晚几分钟爆**

扩池只能作为**争取时间的临时手段**，同时必须有限流。

### 3. `idle-timeout` 别设太短

30 秒回收空闲连接，在低峰期会造成"刚建好又回收、流量一来全在建连接"的抖动。
10 分钟量级更稳（具体的值取决于你的流量形态）。

## 六、应急：先把人救出来，再谈根治

### 释放连接的最快办法是重启

**不需要换 jar，重启就释放全部连接。** 这是应急，不是修复。

### 但配置项能不能靠环境变量改，取决于 jar

如果旧 jar 里写的是硬编码：

```yaml
maximum-pool-size: 20        # 没有 ${APP_DB_POOL_MAX:20}
```

那么**你设了环境变量也不会生效**。此时"改配置 + 重启"是假动作 —— 必须重新打包换 jar。

**上线前先确认这一行有没有占位符。** 没有就写进发版说明：本次必须换 jar。

### 停服只 kill 精确 PID

```bash
pgrep -f 'jar/your-app-exec.jar'    # 精确到 jar 路径
kill $PID
```

**不要 `pkill -f your-app`** —— 它会把同名前缀的其它服务一起杀掉，而且如果这些服务没有守护进程兜底，就再也起不来了。

## 七、验证有效

改完不能只看"没再报错"，要给三条证据：

| 证据 | 怎么取 |
|---|---|
| 池指标回落 | 观察 `active` 是否周期性回到低位、`idle` 是否 > 0 |
| 闸门真的在拦 | 日志里出现降级计数；压测时 `active` 不超过闸门值 |
| 配置真的注入 | 启动时打一行日志，把实际的池大小/闸门值打出来 |

第三条最容易被跳过。环境变量名拼错、profile 没激活、配置被更高优先级的文件覆盖 —— 都不会报错，只会"怎么改都没效果"。

**在初始化处打一行日志，是唯一能证明"你改的那个值真的生效了"的办法。**

## 八、验收清单

- [ ] 确认是"借空"（`idle=0`）还是"DB 拒绝"（`idle>0` 建连失败）
- [ ] 找到占连接的具体形态：无上限并发 / 超时不取消 / 后台批处理 / 长事务
- [ ] 外部方案的四条假设已在本仓逐条验证
- [ ] 限流挂在唯一汇入口，抢不到降级不排队
- [ ] 后台任务并发单独限流 + 总开关
- [ ] `leak-detection-threshold` ≥ `connection-timeout`（或关闭）
- [ ] 没有把"扩池"当根治
- [ ] 应急重启与"换 jar 才能改配置"的区别已写进交付
- [ ] 停服用精确 PID，不用 `pkill -f` 模糊匹配
- [ ] 启动日志打出了实际生效的池大小与闸门值
