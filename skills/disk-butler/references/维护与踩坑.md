# 维护与踩坑

> **这是给"改这个技能的人"看的，不是给"用它的人"看的。** 所以它放在 `references/` 里按需加载，不塞进 `SKILL.md`。
>
> **改完任何文件，先跑一遍自检：**
> ```powershell
> .\scripts\Test-SkillHealth.ps1 -Deep
> ```
> 下面每一条都已经变成了自检里的一项检查——文档会腐烂，检查脚本不会。

## 这个项目的运行环境前提

**目标环境是 Windows PowerShell 5.1**（不是 PowerShell 7）。这不是猜测，是实测：

```
PSVersion  5.1.26100.9444
PSEdition  Desktop
```

**这一个事实决定了后面一半的坑。** PS 5.1 与 PS 7 在这些地方行为不同：

| 行为 | PS 5.1 | PS 7 |
|---|---|---|
| 读取无 BOM 的 UTF-8 文件 | 按 ANSI(GBK) 解释 → **中文乱码** | 按 UTF-8 解释 |
| `Set-Content -Encoding UTF8` | 写 **带 BOM** | 写不带 BOM |
| `Get-Content` 默认编码 | ANSI(GBK) | UTF-8 |
| `Parser::ParseFile` 对无 BOM 文件 | 按 ANSI 解释 → 误报语法错误 | 按 UTF-8 |

## 十二条踩过的坑

### 1. UTF-8 BOM：`.ps1` 必须有，`SKILL.md` 绝不能有

**现象**：脚本在自己机器上跑得好好的，到别人机器上中文全变乱码；或者技能加载后 `description` 是空的。

**根因**：两个方向相反的要求
- `.ps1` **缺 BOM** → PS 5.1 按 GBK 解释 UTF-8 字节 → 中文字符串全乱
- `SKILL.md` **带 BOM** → frontmatter 解析用 `text.startsWith('---')`，BOM 让首字符变成 `\uFEFF` → 判定失败 → 技能描述丢失

**修法**：

```powershell
# 给 .ps1 加 BOM
$b = [IO.File]::ReadAllBytes($path)
[IO.File]::WriteAllBytes($path, ([byte[]](0xEF,0xBB,0xBF)) + $b)

# 给 SKILL.md 去 BOM
$t = [IO.File]::ReadAllText($path, [Text.Encoding]::UTF8)
[IO.File]::WriteAllText($path, $t, (New-Object Text.UTF8Encoding($false)))
```

**⚠️ 特别注意**：本仓库用的 `edit` 工具会**剥掉 BOM**。所以每次编辑 `.ps1` 之后都要重新补 BOM——这是自检里的第一项检查。

### 2. `Get-Content` 不指定编码 → `ConvertFrom-Json` 直接崩

**现象**：`ConvertFrom-Json : 传入的对象无效，应为":"或"}"`，但 JSON 文件看起来完全正常。

**根因**：PS 5.1 下 `Get-Content` 默认按 GBK 读，UTF-8 的中文变成乱码字节，JSON 结构被破坏。

**这个坑在本项目里真实存在过 8 处**（读清理计划、读快照、读迁移记录），只是中文没落在关键位置才没暴露。

**修法**：所有 `Get-Content` / `Set-Content` / `Add-Content` / `Out-File` 显式加 `-Encoding UTF8`。

**防线**：自检里有一条 lint 规则扫描全文。它**用拼接方式构造命令名**（`"$_-" + 'Content'`）而不是写字面量——否则那行搜索模式会匹配到自己，造成误报。

### 3. 环境变量保护过度，砍掉了清理能力

**现象**：扫描器报告 "跳过（被环境变量指向）"，`%TEMP%` 直接消失，一次性损失 500+ MB 的清理能力。

**根因**：`TEMP` 环境变量指向 `%LOCALAPPDATA%\Temp`，于是这条安全规则把整个临时目录都拦掉了。但**"整体删除一个配置位置"和"清理其中的旧文件"是两回事**。

**修法**：按模式区分
- `Mode = 'WholeDir'` → **拒绝**（整体删活跃配置位置 = 破坏环境）
- `Mode = 'AgeFilter'` → 允许，但安全等级**强制从 Safe 降为 Confirm**

**这条是设计规则，不只影响 `%TEMP%`。** 以后新增任何"整体删目录"的分类，都要先想清楚它会不会命中某个环境变量。

### 4. `Join-Path` 空值崩溃

**现象**：`Join-Path : 无法将参数绑定到参数"Path"，因为该参数是空值。`

**根因**：`@($null | ForEach-Object { Join-Path $_ '_npx' })` —— 可选参数为空时，管道仍会迭代一次，`$_ = $null`。

**修法**：先判空再加

```powershell
if ($ExtraSearchRoots) { $npxRoots += @($ExtraSearchRoots | ForEach-Object { Join-Path $_ '_npx' }) }
```

### 5. 重复项在汇总里重复计费

**现象**：汇总说"可释放 X"，实际只能释放 X 的一半。

**根因**：为了提供"7 天 / 30 天两档"，给同一个 `%TEMP%` 加了两个计划项。汇总对 `Bytes` 求和时把它们都算上了。

**修法**：同类同目标只保留一项，用参数控制阈值（`-Days`），需要保守就换参数重跑。

**通用规则**：给汇总加新分类时，检查有没有两个 item 的 `Target` 相同。

### 6. PowerShell 语法三连坑

| 现象 | 根因 | 修法 |
|---|---|---|
| `表达式中缺少右")"` | `if -not $Force) {` 少开括号 | 写 `if (-not $Force) {` |
| `意外的标记 "+"` | `throw (expr) + "..."` | 先拼成一个字符串变量再 `throw` |
| `表达式中缺少右")"`（多行方法） | `.IsInRole(...)` 换行接在 `)` 之后 | 整条表达式写成一行，或先赋给变量 |

**最后一条值得单独说**：PowerShell 不允许在方法调用的 `.` 之前换行。

```powershell
# ❌ 解析失败
if ($x -and -not ([Security.Principal.WindowsPrincipal](
        [Security.Principal.WindowsIdentity]::GetCurrent())
        .IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator))) { }

# ✅ 先算出来
$isAdmin = ([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole(
    [Security.Principal.WindowsBuiltInRole]::Administrator)
if ($x -and -not $isAdmin) { }
```

### 7. 日志写进技能目录 → 被打包发出去

**现象**：`npm pack --dry-run` 里出现 `skills/disk-butler/logs/cleanup-2026....log`。

**根因**：日志默认写在 `$PSScriptRoot\..\logs`，也就是技能目录里；而 `package.json#files` 包含了整个 `skills/`。

**修法**：日志与迁移记录改写到用户数据目录，**技能目录只当只读资源**：

```powershell
$base = if ($env:LOCALAPPDATA) { $env:LOCALAPPDATA } else { $env:TEMP }
$LogDir = Join-Path $base 'disk-butler\logs'
```

再加 `.npmignore` 作双保险。这条不只是打包问题——**技能目录在别人的安装环境里本来就是只读的**。

### 8. 技能布局：目录层级算错导致技能"消失"

**现象**：把技能移进 `skills/disk-butler/` 后，DSH 技能目录里它直接不见了。

**根因**：DSH 的文件系统技能发现**只扫一层**（`<根>/<名字>/SKILL.md`），不支持嵌套。Junction 指向了仓库根，于是 `SKILL.md` 落在第二层，扫不到。

**修法**：Junction 要指向 `skills/disk-butler`，而仓库根要**上溯两级**才能从技能根算出来。

```powershell
$RepoRoot = Split-Path -Parent (Split-Path -Parent $SkillRoot)
```

**为什么要有 `skills/` 这层**：Codex/OpenAI 插件规范要求 `plugin.json` 的 `skills` 字段必须指向名为 `skills` 的目录。这个布局同时满足两套规范。

**⚠️ 连带影响**：`index.js` 的 `resourceBase` 必须指向 `skills/disk-butler`（技能根），不是仓库根——否则 `SKILL.md` 里的 `scripts/`、`references/` 相对引用解析不了。

### 9. "假通过"比报错更危险

**现象**：自检报"打包内容干净"，但实际上 `npm pack` 因为路径错误根本没跑成功，输出为空，正则匹配不到任何坏文件 → 判定为通过。

**根因**：把"没找到问题"等同于"检查通过了"，没有验证**检查本身是否真的执行了**。

**修法**：显式验证工具是否成功执行

```powershell
$out = & npm pack --dry-run 2>&1 | Out-String
if ($LASTEXITCODE -ne 0 -or $out -notmatch 'npm notice') {
    Warn "npm pack 未成功执行，无法判断打包内容"
    $out = ''
}
```

**通用规则**：任何"扫描输出找坏东西"的检查，都要先确认扫描真的产生了输出。

### 10. 自检规则匹配到自己

**现象**：新加的编码 lint 规则把**它自己那一行**报成了违规。

**根因**：那一行里有 `-Pattern 'Get-Content|Set-Content|...'` 字面量，被自己的正则命中。

**修法**：把命令名拼出来，让源码里不出现字面量

```powershell
$encCmds  = @('Get','Set','Add') | ForEach-Object { "$_-" + 'Content' }
$encCmds += 'Out-' + 'File'
$encRe    = '(^|\|\s*)(' + ($encCmds -join '|') + ')\b'
```

### 11. `@()` 作用在 `List[object]` 上会抛异常

**现象**：`@($list)` 报 **"参数类型不匹配"**，即使那个 List 是空的也照炸。

**根因**：PS 5.1 的一个怪异行为——`@()` 对 `List[object]` 不适用，但对其它泛型 List 完全正常：

| 写法 | 结果 |
|---|---|
| `@($l)`，`$l` 是 `List[object]` | ❌ **参数类型不匹配**（连空 List 都炸） |
| `@($l)`，`$l` 是 `List[string]` / `List[int]` / `List[pscustomobject]` | ✅ 正常 |
| `$l.ToArray()` / `[array]$l` / `@($l \| ForEach-Object { $_ })` | ✅ 都正常 |

**修法**：对 `List[object]` 一律用 `.ToArray()`。

**防线**：自检里加了一条静态检查——先找出所有 `= New-Object ...List[object]` 的变量名，再扫有没有 `@($那个变量` 的写法。这个坑只在运行时暴露，静态查最划算。

### 12. `if` 语句的输出会被"单元素拆包"

**现象**：给属性赋一个数组，结果属性变成了**单个对象**，`.Count` 取不到值（返回空而不是 1）。

**根因**：`if` 的输出走管道，而管道对**单元素数组会拆包**：

```powershell
# ❌ $val 不是数组，是那个元素本身
$val = if ($man) { @($man.entries) } else { @() }
[pscustomobject]@{ Entries = $val }      # Entries 是 PSCustomObject，.Count 取不到

# ✅ 把 @() 包在**整个 if 的外面**
[pscustomobject]@{ Entries = @(if ($man) { $man.entries }) }
```

注意这和上一条是**同一族问题**——都是数组的包装/拆包语义。凡是"这个值应该是数组"的地方，`@()` 都要放在**最外层**。

**这个坑是这么暴露的**：隔离区的 `manifest.json` 里 `entries` 确实是数组，但读回来之后 `Entries.Count` 一直是空，表现为"合计 0 项""共 项"这类空白显示——数值本身没错，只是计数坏了，很容易被当成显示小问题而漏掉。

## 本次新增功能时踩到的坑（原样记录）

做 ⭐1~3 三个新功能时，**一次就踩了 4 个坑**，全部发生在"改完没跑自检"的时间窗口里：

| 坑 | 触发动作 | 本可被谁拦住 |
|---|---|---|
| 双引号字符串里套直引号 | 手写 `Write-Host "…「可反悔」…"` 时用了 `"` | 语法检查 |
| **BOM 被编辑工具剥掉** | 用 `edit` 工具改 `.ps1` | `Fix-Bom.ps1`（当时还没有） |
| `@()` 用在 `List[object]` 上 | 写 manifest 时 `@($entries)` | 自检规则（当时还没有） |
| `if` 输出单元素拆包 | `Entries = if (...) { @(...) }` | 只能靠实跑发现 |
| **自检规则又一次误报** | 检测 `@($var)` 的正则写太松，把安全的 `@($var \| 管道)` 也报了 | 收紧成"必须是 `@($var)` 紧接右括号" |

**最后一条值得单独强调**：这是第 10 条（自检规则匹配到自己）的翻版，**同一个毛病在一轮开发里犯了两次**。规律很清楚——

> 写静态检查规则时，**误报比漏报更有害**。漏报只是少查一个，误报会让人开始无视检查器的输出，最终整套防线失效。
>
> 所以规则要**收紧到只报确定的坏形态**，拿不准就不报（留给实跑去发现）。

自检里那条 `@($var)` 规则现在只匹配**变量名后紧跟右括号**的形式。因为实测确认：

| 形式 | 安全性 |
|---|---|
| `@($list)`（`$list` 是 `List[object]`） | ❌ 炸 |
| `@($list \| Sort-Object ...)` | ✅ 安全（管道先拆开，`@()` 再重新包成数组） |
| `@($list \| Where-Object ...)` | ✅ 安全 |
| `@($list.ToArray())` | ✅ 安全 |

前三个现在都有自动防线了。**第四个（`if` 拆包）目前只能靠实跑发现**——它不报错，只是让计数变成空，是那种最容易滑过去的静默错误。所以"改完必做"里的第 3 步（真实跑一次）不能省。

**第 2 步很重要**：`self-test.mjs` 用 mock 的 Cordis 上下文真的调用 `apply()`，能验证 frontmatter 解析、技能注册、`resourceBase` 指向——这些在纯语法检查里看不出来。
