# .env 配置引导

配置缺失时最常见的失败不是"报错"，是**静默跑偏**：路径为空当成当前目录、密钥为空就去调接口、开关没设就用了默认值。所以缺配置必须**在进入主流程之前**拦住，而不是等出了问题再回头猜。

## 什么时候用

- 技能要从 `.env` 读工作目录 / 仓库路径 / 密钥，但读不到。
- 变量存在但值为空、值是占位符（`your-key-here`、`xxx`、`changeme`）。
- 值是路径，但那个目录不存在（拷了别人的 `.env`、换了机器、仓库没 clone）。
- 用户刚拉下仓库，第一步就卡住。

## 三层检查，逐级往下

```
.env 存在?
  ├─ 否 → 第一层：给出创建方式，别自己造一份
  └─ 是 → 变量有非空值?
           ├─ 否 → 第二层：问值，问完写进去
           └─ 是 → 值有效?
                    ├─ 否 → 第三层：验证并纠正
                    └─ 是 → 进入主流程
```

**任何一层都不许跳。** 尤其不要"变量为空就当没配、悄悄用默认值继续跑"——那等于把故障推迟到几十分钟后，还带上错误的上下文。

## 第一层：`.env` 不存在

先看仓库里有没有 `.env.example` / `.env.template` / `.env.sample`。**有就复制，没有才问用户**。

```bash
test -f .env && echo EXISTS || echo MISSING
ls -1 .env.example .env.template .env.sample 2>/dev/null
```

话术（照这个意思说，别照抄字面）：

> 项目根目录没有 `.env`。这个文件放本机专属配置，不进 Git。
> 仓库里有 `.env.example`，我按它复制一份 `.env` 出来，然后只改需要改的项——可以吗？

两条硬规矩：

1. **绝不凭猜测编造密钥**。占位符会一路跑到接口调用才炸，比直接缺配置更难查。
2. **绝不把 `.env` 加进 Git**。先确认 `.gitignore` 里有它；没有就先补，再创建文件。

## 第二层：变量为空

读出来判断"有值"时注意三种假有值：

| 现象 | 处理 |
| --- | --- |
| `KEY=` | 空值，等于没配 |
| `KEY="  "` | 去掉引号和空白后再判断 |
| `KEY=your-key-here` / `xxx` / `changeme` / `TODO` | 占位符，按空值处理 |

问用户时**一次问全**，别一个一个挤牙膏：把缺的变量列成表，每个带上"这是什么、从哪拿、示例长什么样"。

话术：

> `.env` 里这些项还是空的，需要你给值：
> - `XXX_PATH` — 要操作的仓库在本机的绝对路径（例：`D:/work/my-repo`）
> - `XXX_KEY` — 服务的 API Key，在控制台 → 密钥管理里生成
>
> 给我值我就写进去；密钥这类你不想贴到对话里的，也可以自己填，填完告诉我一声，我复查格式。

**密钥不要回显。** 写进文件后，后续回复里只说"已配置"，不打印原文。

## 第三层：值无效

按类型分别验，别一把梭：

| 类型 | 判据 | 常见错 |
| --- | --- | --- |
| 路径 `*_PATH` / `*_DIR` | `test -d` / `test -f` 真的存在 | 拷了别人的 `.env`；`\` 与 `/` 混用；有空格没引号 |
| URL `*_URL` / `*_ENDPOINT` | 协议 + 主机可解析，路径拼对 | 少了 `http://`；末尾多了 `/` 导致拼出 `//` |
| 端口 / 数字 | 在合法范围 | 当成字符串比较导致 `"8080" != 8080` |
| 开关 `*_ENABLED` | 只有 `true`/`false`（或 `1`/`0`），且**代码里认哪个要一致** | 写 `yes`、`on`、`TRUE`，只有部分框架认 |
| 密钥 / Token | 长度、前缀符合该服务格式 | 复制时带了换行或前后空格 |

路径不存在时，别急着说"路径错了"，先分清三种：

1. **真错了** → 问正确位置。
2. **仓库还没 clone** → 提示先 clone，或问要不要 clone 到哪个目录。
3. **是相对路径**（`./xxx`）→ 相对的是**进程工作目录**，不是 `.env` 所在目录。这种最容易"在 A 目录跑正常、在 B 目录跑就找不到"，建议一律改成绝对路径。

## 多环境与 CI

- `.env` 只放**本机**、**单人**的值。多环境用 `.env.local` / `.env.test` 这类分层，把"哪个优先"写进 README，否则排查时永远说不清用的哪份。
- CI 里**没有 `.env`**，靠环境变量注入。所以代码读配置的顺序必须是「进程环境变量 → `.env` 文件 → 默认值」，反过来会让 CI 静默用默认值。
- 别在代码里硬编码回退路径（`/home/me/work`）。默认值要么是安全的中性值，要么干脆不设、缺了直接报错。

## 常见的假解决

| 做法 | 为什么不行 |
| --- | --- |
| 变量为空就用默认值继续 | 故障推迟到下游，排查成本翻十倍 |
| 临时 `export XXX=...` 然后说配好了 | 换个终端、重启 IDE 就没了；要落到 `.env` 并说明 |
| 编一个看起来像真的 key | 一定会在调用时才炸，且报错指向别处 |
| 把 `.env` 提交进 Git 方便队友 | 密钥泄露；且队友会覆盖你的值 |
| 改代码去迁就错的配置 | 配置是外部输入，代码不该为它让步 |

## 自检（改完必须跑）

```bash
# 1. 文件在且被忽略
test -f .env && echo "env ok"; git check-ignore -q .env && echo "ignored ok"

# 2. 必填项非空（把变量列全）
for v in XXX_PATH XXX_KEY; do
  val=$(grep -E "^${v}=" .env | cut -d= -f2- | tr -d '"'"'"' ')
  [ -n "$val" ] && echo "$v ok" || echo "$v EMPTY"
done

# 3. 路径型变量真存在
test -d "$(grep -E '^XXX_PATH=' .env | cut -d= -f2-)" && echo "path ok"
```

三条都过，再说"配置好了"。只跑了第一条就宣布完成，等于没验。

## 报告纪律

收尾时说清楚三件事：**建了/改了什么文件**、**哪些变量是新填的（密钥只说已填不说值）**、**下一步跑什么命令**。如果用户拒绝提供某个值，明确写"该项仍缺，主流程会在 X 处停下"，不要含糊过去。
