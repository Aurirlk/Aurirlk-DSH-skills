# 文档与代码同步

这个技能主张一件事：

> **改代码不更文档，视为未完成，不应提交。**

不是"文档很重要"这种空话。理由是具体可查的：文档写错了，调用方按文档写代码，失败在现场；而写文档的人早就不记得当时怎么想的了。**文档的错误比代码的错误传播得更远**，因为代码有编译器兜着，文档没有。

## 提交前的映射检查（必做）

```bash
git diff --name-only        # 先看这轮到底动了什么
```

按下表判定必更新的文档。**只改 `.md` 本身时跳过本表**。

| 改动了什么 | 必须同步 |
| --- | --- |
| 接口路径、请求/响应结构、认证头 | 接口文档里的路径、请求体、认证示例 |
| 新增或删除功能、模块、工具 | 介绍页的能力清单、README、对应架构文档 |
| 配置项、默认值、开关 | 配置说明；有"默认值"表格的也要改 |
| 表结构、DDL、迁移脚本 | 数据模型文档 + 脚本文件名（文档里常写着旧文件名） |
| 架构、链路、责任链节点 | 架构文档、概念说明 |
| 能力状态变化（上线/下线/占位/默认关） | 状态表、"当前边界"章节、README |
| 依赖版本、JDK/运行时版本 | 环境要求、构建说明 |
| 部署脚本、镜像、编排文件 | 部署手册里的命令（最容易漏，因为改的人不跑它） |
| 纯文档改动 | 只保证链接有效、不自相矛盾 |

**这张表的意义是"不许凭感觉"**。凭感觉的结果是：接口改了文档没改（因为"文档不是顺手的事"），而配置项改了文档改了（因为"我记得有这页"）。你以为自己在保持一致，其实只在有记忆的地方一致。

## 信息真源优先级

文档和实现冲突时，按这个顺序采信，**冲突就改文档，不改代码去迁就旧文档**：

1. **当前源码**（Controller、DTO、拦截器、常量）
2. **运行时可执行资产**（迁移脚本、编排文件、打包脚本）—— 它们会真的被执行
3. **构建配置**（`pom.xml` / `package.json` 的版本、模块、依赖基线）
4. **应用配置文件**（`application.yml` 之类的键与默认值）
5. **站点/文档配置**（导航、侧边栏）
6. **现有文档** ← 最不可信的一层

为什么把现有文档排最后：它是上一轮的结论，可能基于当时的代码。而排第 2 的脚本之所以排在构建配置之前，是因为**脚本会被执行，猜不出来**——文档里写"用 A 脚本初始化"而实际是 B，照着做的人直接失败。

## 五条判定原则

**1. 删掉不存在的东西，不留"兼容说明"当挡箭牌**

功能已经移除，就从能力清单里删掉。不要写"旧版支持 X，现已改用 Y"——这条只对正在迁移的用户有用，而他们需要的是迁移指南，不是能力清单里的幽灵条目。

**2. 不要把规划写成能力**

三种东西必须写进"当前边界"而不是"支持清单"，并且标注条件：

- 占位实现（接口在，逻辑是空的）
- 默认关闭的开关
- 代码就绪但依赖缺失（驱动没有、脚本没写、模块没引）

判据要硬：一项能力算"当前支持"，必须**同时**存在匹配的路由、实现、存储结构、配置。少一样就是部分支持。

**3. 能力归属按"谁提供"写，不按"有没有同名类"写**

禁止用"上游有、本仓没有"、"未迁移"这类描述来描述能力。某项能力由另一个模块承担时，直接写承接模块的名字。只有平台确实不设这个机制，才在"设计取舍"里说明原因。

写之前**先全仓搜承接方**，别凭印象说"没有"。

**4. 文档是介绍项目，不是研发过程档案**

正文只写：这是什么、怎么用、能力由谁提供、边界在哪。

迁移差异、整改台账、事故复盘、时间线、证据链、待办排期——全部挪进归档目录，头部标「时点 + 现已被谁取代 + 只读，不作为现状依据」。

不加这条的后果很具体：正文越写越长，读者分不清哪句是现状、哪句是三个月前的临时状态。

**5. 跨仓事实也要写**

前端示例、客户端常量、认证头的旧名兼容约定——只要影响调用方，就得有文档，哪怕代码不在这个仓。

典型的坑：认证头为了兼容老客户端保留了旧品牌名，但上下文路径是新名字。文档不写明这个不兼容点，外部集成方会照着头部名字去猜路由。

## 完成前的残余扫描

改完不是结束。旧名字会残留在文档里，而且 grep 不出来的地方最危险（大小写、连字符、缩写）。

```bash
# 旧路径 / 已迁走的目录
rg "old/path|legacy/dir" docs --glob '!**/node_modules/**' --glob '!**/dist/**'

# 旧版本号（升级后最容易忘）
rg "Java 17|Node 18|Vue 2" docs --glob '!**/node_modules/**'

# 已删除的页面/文档名
rg "removed-page|old-guide\.md" docs .

# 旧认证头/旧字段名（只应出现在兼容说明里）
rg "Old-Header-Name" docs
```

预期结果：**每一条要么零命中，要么出现在明确标注为"历史/兼容"的章节里**。出现了但没标注，就是漏改。

## 构建验证

```bash
pnpm --dir docs install --frozen-lockfile
pnpm --dir docs docs:build
```

三条纪律：

- **没跑成功不许说成功**。写"已构建通过"而实际没跑，是这个技能最不能接受的行为——它比不写文档更糟，因为它让人误以为可以发布。
- 网络不可用时用 `--skip-install` 之类的等价方式，但**必须明说用了替代方案**。
- 构建通过 ≠ 内容正确。构建只证明链接没断、语法没崩。

## 报告纪律

汇报时说这几件事，而不是逐行 diff：

- 改了哪些**文档区域**（不是每行）
- 哪条校验命令**失败**了、为什么
- 有意保留的引用（changelog 历史、源码默认值和推荐值不一致的地方）
- 如果某项该改而没改，说明原因和风险

## 坑表

| 现象 | 真因 | 处理 |
| --- | --- | --- |
| 提交里只有 `.java`，`docs/` 一行没动 | 没做映射检查 | 用上面的表逐行过 |
| 文档说"已支持"，实际是占位 | 把规划写成能力 | 移进"当前边界"并标条件 |
| 接口文档的认证示例是旧的 | 只改了 DTO 没改示例 | 示例和结构一起改 |
| 文档写着旧脚本名 | 脚本重命名时没搜 | 残余扫描第一条 |
| 侧边栏点进去 404 | 页面移动/删除没改 nav/sidebar | 移动页面必须同步配置 |
| 把结论写进工作日志就当更完文档 | 日志不进文档站索引 | 日志 ≠ 文档 |
| 构建"通过"但没人跑过 | 口头声明 | 只报真实执行的命令 |
| 正文里塞了三个月的整改台账 | 没做归档 | 挪进 archive 并标时点 |

## 自检清单

- [ ] `git diff --name-only` 过了一遍映射表，每一项都有对应文档改动
- [ ] 冲突处以源码为准，没有改代码迁就旧文档
- [ ] 已移除的能力从清单里删掉了，没留"兼容说明"
- [ ] 占位/默认关/缺依赖的，写进了"当前边界"并标了条件
- [ ] 能力归属写的是承接模块，全仓搜过，不是凭印象
- [ ] 移动或删除的页面，nav / sidebar 同步了
- [ ] 残余扫描零命中，或命中处都标了"历史/兼容"
- [ ] 构建命令**真的跑过**，失败就如实说
