# docs-code-sync

> 本技能是 [Aurirlk DSH Skills](../../README.md) 合集的一员 · [← 返回仓库目录](../../README.md)

**中文** | [English](README.en.md)

改了代码不改文档，等于没改完。

## 这玩意儿治什么

接口改了个字段，文档里还是旧结构。配置项换了个默认值，配置说明还是旧的。功能下线了，能力清单里还挂着。

这类问题的特别之处是**它不会报错**。代码有编译器兜着，文档没有。所以错误会一直躺着，直到某个外部集成方照着文档写完、联调、失败，再回头找是谁写的——而写的人早忘了。

这个技能的核心主张就一句：

> **改代码不更文档，视为未完成，不应提交。**

## 关键机制：改完先过一张表

`git diff --name-only` 出来，对着「改动 → 文档」映射表逐行判定。接口、配置项、表结构、模块、能力开关、依赖版本、部署脚本，每一项都有对应的必更文档。

为什么非要表格：

- 凭感觉的结果是**在记得的地方一致**——接口改了没更（"文档不是顺手的事"），配置改了更了（"我记得有这页"）。
- 部署脚本是最容易漏的，因为改的人自己不跑它。

## 真源优先级：文档排最后

```
当前源码 > 可执行脚本 > 构建配置 > 应用配置 > 站点配置 > 现有文档
```

冲突一律改文档，**不许改代码去迁就旧文档**。

两个排序有理由：

- **可执行脚本排在构建配置之前**——脚本会被执行，猜不出来。文档写"用 A 脚本初始化"而实际是 B，照着做的人当场失败。
- **现有文档排最后**——它是上一轮的结论，可能基于当时的代码。

## 两条最常被违反的判定

**"不要把规划写成能力"**

占位实现、默认关闭的开关、代码就绪但依赖缺失——这三种必须进"当前边界"并标条件，不许进"支持清单"。

判据是硬的：算"当前支持"必须同时有**路由、实现、存储结构、配置**，少一样就是部分支持。

**"文档是介绍项目，不是研发过程档案"**

正文只写：这是什么、怎么用、能力由谁提供、边界在哪。

迁移差异、整改台账、事故复盘、时间线、证据链——全部挪进归档目录，头部标「时点 + 现已被谁取代 + 只读」。

不加这条，正文会越写越长，读者分不清哪句是现状、哪句是三个月前的临时状态。

## 完成前还要做残余扫描

旧名字会留在文档里，而且 grep 不出来的地方最危险（大小写、连字符、缩写）。

```bash
rg "old/path|legacy/dir" docs --glob '!**/node_modules/**'
rg "Java 17|Node 18" docs
rg "removed-page\.md" .
```

要求：**每一条要么零命中，要么出现在明确标注"历史/兼容"的章节里**。

## 一条不能破的纪律

**没跑成功不许说成功。**

写"已构建通过"而实际没跑，比不写文档更糟——它让人误以为可以发布。网络不通时可以用 `--skip-install` 之类的等价方案，但必须明说用了替代。

## 什么时候会用到

- 改了接口 / 配置 / 表结构，准备提交。
- 要审一份文档，看它有没有把"计划中"写成"已支持"。
- 文档站侧边栏点进去 404。
- 交接前想确认文档和代码还是同一套。

## 安装

```bash
pnpm add github:Aurirlk/Aurirlk-DSH-skills
# 或单挂
ln -s "$PWD/skills/docs-code-sync" ~/.dsh/skills/docs-code-sync
```

## 它不管什么

- 不管文档站用什么框架（VitePress、Docusaurus 都一样适用）。
- 不管排版美化。
- 不管写新文档——那是写作，这是**核对**。
