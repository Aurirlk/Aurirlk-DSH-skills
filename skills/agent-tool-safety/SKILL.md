# Agent 工具的安全边界

给 agent 一把只读的铲子，最坏结果是查不到数据。
给它一把能写库的铲子，**最坏结果是它一边道歉一边把生产改了**。

这条技能管的不是"工具怎么写"，是"**工具怎么让模型不能骗人、也不能骗自己**"。

## 一、命名就是契约

| 工具名 | 模型的自我认知 | 后果 |
|---|---|---|
| `update_agent_prompt` | "我改了" | 回答"已为您更新" —— 实际只进了暂存区 |
| `draft_agent_prompt` | "我起草了" | 回答"已生成草稿，等你确认" —— 与事实一致 |

**写工具一律 `draft_*`。** 这不是命名风格，是**用命名约束模型的宣称**。
一旦名字里带 `update` / `save` / `apply`，模型在总结时几乎必然说"已改好"。

配套：

- **读工具给全文**（`read_agent_prompt`），画像类工具只给**预览**（600 字）。只给预览又问细节，模型只能编。
- 业务域前缀（`business_`、`data_`）—— 同类工具多了，模型靠名字区分作用域。

## 二、双层确认：草稿 ≠ 待批 ≠ 已生效

一个"在建"的对象和一个"待批"的变更，是两种状态，**不能塞进同一张表**：

| 层 | 表 | 状态机 | 谁看 |
|---|---|---|---|
| **在建草稿** | `*_draft` | `BUILDING → READY → COMMITTED / DISCARDED` | 操作者，随时可丢 |
| **待批变更** | `*_change` | `DRAFT → APPLIED / REJECTED`（带 `rollback_json`） | 审批者，可回滚 |

草稿**不进**变更表 —— 否则用户还没建完就出现在待办列表里，审批的人要面对一堆半成品。

变更表必须带 `rollback_json`（逐条写），否则"回滚"只是把状态改回去，数据已经错了。

## 三、scope：两套自增序列会撞号

变更表里存 `agent_id` 时，如果它可能指向**两个不同实体**（比如语义模型的 agent 和业务 agent 各有一套自增 id），那么 id=5 有两种含义。

**必须加 `scope` 列，并在三个地方校验：**

1. **起草时**写死（不接受模型传入）
2. **查询时**强制带（列表、详情、按 id 取）
3. **应用 / 回滚前**强校验（不匹配直接拒绝）

三道缺一道，就可能"应用业务智能体的简介变更，却改了数据智能体的语义模型"。这种错误不报错、不崩，只是数据慢慢变脏。

## 四、apply 的写法：只回写定向列

真实事故形态：

```
markBatchApplied(batch)   // 先把状态改成 APPLIED
for (row : rows) {
    updateById(row)       // ← row 是之前查出来的，status 还是 DRAFT
}                         //   整行回写 → 状态被覆盖回 DRAFT
                          //   → 回滚接口被状态机拒绝（"不是 APPLIED"）
```

### 规则

1. **先改状态，再逐行处理**（顺序不能反）。
2. **回写只写变化列**（`UPDATE ... SET rollback_json = ? WHERE id = ?`），不要 `updateById(整行)`。
3. **`null` 不等于"不更新"**：用 `LambdaUpdateWrapper.set()` 显式赋值，`updateById` 会跳过 null 字段 —— 想清空一个字段就永远清不掉。

这条对所有"状态机 + 批量处理"的链路都成立，不只是 agent。

## 五、开关必须做在装配层

框架的"只读 / EXPLORE 模式"常常**管不到自定义工具**。

实证过的情况：某个框架的权限引擎签名写死基类，自定义实现直接 return `ALLOW`，**根本不进权限检查**。所以"我把模式切成只读了"是假的。

### 规则

**开关做在装配层：关闭即不注册。**

```java
// 正确
Toolkit tools(arg, boolean writeEnabled) {
    List<AgentTool> list = new ArrayList<>(readTools(arg));
    if (writeEnabled) list.addAll(writeTools(arg));   // 不注册 = 模型看不见
    return new Toolkit(list);
}
```

模型看不见的工具，它不会幻觉去调 —— 比"注册了但拒绝执行"干净得多。

### 默认 fail-closed

前端传"完全访问"才开写；缺字段、解析失败、未登录 → **一律关**。
默认开的写权限，早晚会在某个没人测的入口被打开。

### 双开关是"与"关系

运维级总开关 × 产品级开关：

```yaml
app.sandbox.enabled      AND   product.sandbox.enabled
```

**两个都开才生效。** 关掉时：工具不注册，**提示词里也不拼这段能力说明**。
只关工具不关提示词 = "看得见调不通"，比完全不提供更糟 —— 模型会反复尝试、反复失败、把错误答案包装成"系统繁忙"。

## 六、沙箱执行面：三条边界

当 agent 要跑脚本 / 跑代码，执行面比工具面更危险。

### 1. 容器读宿主目录只许 `:ro`

代码、数据集、配置挂只读。写只允许落到明确的产物目录。

### 2. 容器永不连库

SQL 在宿主执行完 → 结果写成 CSV → 挂进容器做分析。

一旦让容器直连数据库，表级白名单、租户隔离、只读账号这些护栏**全部绕开** —— 因为绕过它们的是一条全新的连接。

### 3. 结果要能判真假

脚本产物的 `ok` 只表示"**脚本本身跑成功**"，不等于业务结论成立。
业务结论另给字段（`clean` / `counts` / `passed`）。

撞过的坑：lint 脚本用 `ok` 表示"语义模型没问题"，宿主门面把 `ok=false` 当"脚本挂了" → 整份报告丢弃、只回一句"未给出原因"。

### 容器内的两个必备环境变量

非 root 用户（常见 65534）没有家目录，`/tmp` 往往只是个 64MB tmpfs：

```bash
env HOME=$WS TMPDIR=$WS/tmp MPLCONFIGDIR=$WS/.mpl LANG=C.UTF-8 python3 script.py
```

不设的后果：pip 缓存失败、matplotlib 缓存失败、**中文全变方框**。
另外镜像里**必须真的有运行时** —— 默认 `ubuntu:22.04` 没有 `python3`，表现为 `exit=127`，看起来像"脚本不存在"。

## 七、工具输出的形态决定回答质量

对话"啰嗦 / 全是术语 / 用户看不懂"，根因常常不在提示词，在**工具返回的形态**。

反例：`list_findings` 逐条倒 `[SEVERITY] 名称（CODE）` + 一段证据 JSON。
模型拿到这个，**只能原样转述** —— 它没有别的材料。

正例：工具层直接出人话摘要（去 CODE、同类合并、先给"能不能用"），再加一条输出契约。

**工具是模型的眼睛。眼睛看到的是日志，嘴里说的就是日志。**

## 八、接线自检

写完一个新工具/新字段/新服务，全仓 grep 一次：

- 有调用者吗？零调用者 = **没接入**（"实现了类但没接电"，最容易在评审里蒙混过关）
- 有测试吗？没有测试的关键路径，等于没有回归能力
- 配置项真的被读了吗？环境变量名写错不会报错，只会"怎么改都不生效"

## 九、自检

- [ ] 写工具名是 `draft_*`，不是 `update_*` / `save_*`
- [ ] 草稿与待批变更分表，状态机明确
- [ ] 变更带 `scope`，起草 / 查询 / 应用三处都校验
- [ ] apply 先改状态，回写只写定向列
- [ ] 开关在装配层；关闭即不注册；默认 fail-closed
- [ ] 双开关是"与"；关掉时提示词也不拼
- [ ] 沙箱只读挂载；容器不连库
- [ ] 产物 `ok` 与业务结论分离
- [ ] 容器内设了 `HOME` / `TMPDIR` / `MPLCONFIGDIR`
- [ ] 新增工具/字段全仓有调用者
