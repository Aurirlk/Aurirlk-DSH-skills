# 场景 01 · 代码开发与测试

> 配套 [`../SKILL.md`](../SKILL.md)。四阶段不变，**变了的是"证据"的定义**。

## 一、这个场景的第一原则

> **没跑过、没读过的，不许断言。**

代码领域最常见的问题不是判断错，是**在没验证的前提下用经验下结论**。

- 「这段逻辑肯定没问题」——读过吗？跑过吗？
- 「应该是并发问题」——有复现吗？有日志吗？
- 「加个 try-catch 就好了」——根因在哪？

## 二、四阶段在代码里的样子

### 阶段一 · 事实提取

| 要提取的 | 怎么提 |
|---|---|
| **输入** | 报错信息原文、堆栈、复现步骤、环境版本 |
| **当前实现** | 相关代码路径（不是整个项目，是调用链）、配置项、依赖版本 |
| **实际行为** | 真实的输出/日志/指标，**不是你以为的输出** |
| **预期行为** | 依据是什么（文档？测试？产品说明？） |

**「预期」必须有出处。** 没有出处的"预期"只是个人偏好。

### 阶段二 · 假设与排他

代码里的假设池通常来自五个层次，**从上往下排**：

```
1 环境层：版本、配置、依赖、部署差异
2 输入层：数据形态、边界值、编码、空值
3 逻辑层：分支遗漏、条件写反、边界符号
4 并发层：竞态、锁粒度、顺序依赖
5 资源层：连接、内存、句柄、超时
```

**排查顺序应该从下往上（资源→并发→逻辑→输入→环境）还是反过来？**

答案是：**从"最便宜的验证"开始，不是从"最可能的"开始。**

> 环境层验证只要 30 秒（`node -v`），逻辑层验证要读 200 行。先验证便宜的。

### 鉴别动作示例

| 分不清 | 一个动作就能分开 |
|---|---|
| 环境问题 vs 代码问题 | 在本地最小复现跑一次：能复现 → 代码；不能 → 环境/数据 |
| 并发问题 vs 逻辑问题 | 单线程跑一遍：正常 → 并发；同样错 → 逻辑 |
| 输入问题 vs 逻辑问题 | 用固定数据替换输入：正常 → 输入；同样错 → 逻辑 |
| 这个版本引入 vs 一直存在 | 切到上个版本：正常 → 本次改动引入 |

**这些都是二值的，5 分钟内能做完。**

### 阶段三 · 根因溯源

**下潜四问：**

```
是什么触发了它？
→ 为什么这段代码允许这个触发条件存在？
→ 为什么测试没覆盖到？
→ 为什么上线后没有第一时间被发现？
```

**第三第四问是拉开差距的地方。**

只回答第一问 → 修了一个 case。
回答到第三问 → 补了一类测试。
回答到第四问 → 改了发布流程。

### 阶段四 · 处置与防御

| 级 | 代码场景的典型动作 |
|---|---|
| **应急止损** | 回滚、熔断开关、降级、加白名单、限流 |
| **根治修复** | 改逻辑 + **补一个能复现该 bug 的测试** |
| **长效防御** | 见下 |

**根治修复必须带测试。** 没带测试的修复等于没修——下次重构会原样复发。

### 长效防御的代码版三件套

| 维度 | 具体做法 |
|---|---|
| **环境** | 版本锁定、配置 schema 校验、依赖锁文件 |
| **监控** | 关键路径埋点、错误率告警、慢查询阈值 |
| **流程** | CI 门禁、类型检查、review checklist、灰度发布 |

**只有监控没有流程** → 下次换个入口照样中。
**只有流程没有监控** → 出了问题还是靠用户报。

## 三、这个场景的高频错误

| 症状 | 根因 | 修法 |
|---|---|---|
| 猜一个原因就开始改 | 跳过了事实提取 | 先写现象，再写推断 |
| 改了三处"顺便优化" | 一次改多个变量，无法归因 | 一次只改一处，改了先验证 |
| 修完没测试 | 没用红绿验证 | 先写失败测试，再修到通过 |
| 复现不了就"已解决" | 没有根因，只是现象消失 | 说清"未复现 + 下一步怎么抓" |
| 防御写成"以后注意" | 没找到系统性原因 | 加门禁，不加提醒 |

## 四、输出片段

```markdown
## 现象
- 报错原文：`TypeError: Cannot read properties of undefined (reading 'id')` @ `order.ts:142`
- 触发路径：提交订单 → 优惠券为空时
- 环境：Node 20.11 / 生产 / v2.3.1

## 假设与排他
| 假设 | 支持 | 反对 | 置信度 |
|---|---|---|---|
| 优惠券接口返回 null 未判空 | 堆栈指向 142 行 | — | 高 |
| 上游数据缺失 | 部分订单无优惠券 | 老版本同样数据正常 | 低 |

## 根因
- 直接原因：`coupon` 为 null 时直接取 `.id`
- 系统诱因：该分支无单测；CI 覆盖率未设下限；类型定义用 `any`

## 处置
- ① 止损：回滚 v2.3.1
- ② 修复：可选链 + 补 3 个用例（null / undefined / 空对象）
- ③ 防御：
  - 环境：`strictNullChecks` 打开
  - 监控：优惠券接口返回值 null 率告警
  - 流程：CI 覆盖率下限 70%，`any` 数量设门禁
```
