# 场景 04 · Bug 根因回复

> 配套 [`../SKILL.md`](../SKILL.md)。这个场景的特殊之处：**你交付的不只是结论，是一段话。**

## 一、这个场景的第一原则

> **回复的质量 = 对方能不能自己判断"这是不是我的问题"以及"我该怎么办"。**

技术正确但没人看懂的回复，等于没回复。

## 二、四阶段在 Bug 回复里的样子

### 阶段一 · 事实提取

Bug 报告通常信息不全。**第一阶段的产出往往是一份"缺口清单"。**

| 要素 | 没有会怎样 |
|---|---|
| 现象原文（原话/截图/报错） | 你复现的是另一个问题 |
| 复现步骤 | 只能猜 |
| 环境（版本/系统/浏览器/数据量） | 结论无法迁移 |
| 发生频率（必现/偶发/一次） | 无法判断严重度 |
| 影响的用户范围 | 无法排优先级 |
| 最近变更（发版/配置/数据） | 漏掉最常见的原因 |

### 阶段二 · 假设与排他

#### 2.1 先判"是不是 Bug"

这一步必须先做。四类里只有第一类是 Bug：

| 类别 | 特征 | 回复重点 |
|---|---|---|
| **真缺陷** | 不符合设计预期 | 承认 + 根因 + 修复计划 |
| **设计如此** | 符合设计但不符合期望 | 解释设计 + 记录为需求 |
| **用法问题** | 用户操作路径非预期 | 给正确用法 + 判断是否该优化 |
| **环境问题** | 特定环境/数据导致 | 说明条件 + 给规避方法 |

**把"设计如此"当 bug 修，和把 bug 当"用法问题"敷衍，都是失败。**

#### 2.2 鉴别动作

| 分不清 | 一个动作分开 |
|---|---|
| 真缺陷 vs 设计如此 | 查设计文档/上一个版本行为：一致 → 设计如此 |
| 是普遍问题还是个别 | 用不同账号/数据试：只有他能复现 → 数据相关 |
| 本次引入 vs 历史存在 | 切上个版本：正常 → 本次引入 |

### 阶段三 · 根因溯源

回复里**必须能说清三件事**：

1. **为什么会发生**（机制，不是现象）
2. **影响范围**（哪些用户/数据/场景）
3. **什么时候开始的**（引入版本或时间点）

**只给第一件的回复，对方无法判断自己要不要紧急处理。**

### 阶段四 · 处置与回复

#### 4.1 处置排序

| 优先级 | 判据 |
|---|---|
| **P0** | 数据丢失/安全问题/大面积不可用 |
| **P1** | 核心功能不可用，有规避方案 |
| **P2** | 功能受损，不影响主流程 |
| **P3** | 体验问题 |

**判优先级要写依据。** 「我觉得挺严重的」不是依据。

#### 4.2 回复的四段结构

```markdown
① 结论先行：这是不是问题、严重程度、影响范围
② 原因说明：为什么会发生（机制层面，不甩术语）
③ 当前动作：正在做什么、什么时候有结果
④ 你可以做什么：规避方案或临时办法
```

**四段缺一不可，尤其是第 ④ 段。** 只告诉对方"我们在修"是最让人焦虑的回复。

## 三、回复的六条纪律

1. **先承认，再解释。** 顺序反了就是辩解。
2. **不用"应该是"。** 不确定就说"目前判断是 X，还在验证"。
3. **不甩锅给用户。** 即使是用法问题，也要先说明"哪里容易误解"。
4. **给时间点，不给"尽快"。** 「今天 18:00 前给结论」优于「尽快」。
5. **不用技术术语当挡箭牌。** 对方听不懂 = 你没说清。
6. **不承诺做不到的事。** 宁可说"需要评估"，不要承诺"明天修好"。

## 四、五种典型回复模板

### A · 确认为缺陷

> 已确认这是缺陷，影响 ____（范围）。原因是 ____（一句话机制）。已排入修复，预计 ____ 前给出方案。临时规避：____。

### B · 设计如此

> 这是当前的设计行为：____。你期望的 ____ 我们会作为需求记录（编号 ____）。如果你需要，现在可以这样达到目的：____。

### C · 用法问题

> 这个现象是因为 ____（机制）。正确的用法是 ____。不过这里确实容易误解，我们会在 ____ 处加提示。

### D · 环境/数据相关

> 这个问题只在 ____ 条件下出现（你的环境符合）。原因是 ____。规避方法：____。我们会在下个版本兼容这个情况。

### E · 暂无法定位（熔断）

> 目前能确认 ____，但无法区分 ____ 和 ____。需要你补充 ____（具体到怎么采集）。在此期间建议先 ____（零风险动作）。我会在 ____ 前给出进一步结论。

**E 类是最考验人的。** 大部分人的做法是含糊其辞或拖着不回，正确做法是**明确说出缺什么、并给一个临时动作**。

## 五、这个场景的高频错误

| 症状 | 根因 | 修法 |
|---|---|---|
| 回复很长但对方还在问 | 结论没放开头 | 第一句就给判定 |
| 被追问三次才说清 | 只讲了现象没讲机制 | 补"为什么会发生" |
| 对方反复来问进度 | 没给时间点 | 给具体时刻 |
| 修完了对方说"还是有" | 修的是现象不是根因 | 补复现测试 |
| 争论"这不是 bug" | 没先判类别 | 先归类再回复 |

## 六、自检

- [ ] 第一句是结论，不是寒暄
- [ ] 说清了为什么会发生（机制层）
- [ ] 说清了影响范围
- [ ] 给了明确时间点
- [ ] 给了对方能立刻做的规避动作
- [ ] 没有"应该是""大概"
- [ ] 没有把不确定包装成确定
