# 场景 03 · 事件溯源

> 配套 [`../SKILL.md`](../SKILL.md)。这是四阶段最原始的用法：**一件事是怎么发生的。**

## 一、这个场景的第一原则

> **时间线先于因果。先建立"发生了什么"，再讨论"为什么"。**

几乎所有事故复盘的失败，都是因为把两件事混在一起做——一边理时间线一边找责任，结果时间线被叙事污染。

## 二、四阶段在事件溯源里的样子

### 阶段一 · 事实提取

#### 1.1 建立时间线（第一优先级）

| 列 | 内容 |
|---|---|
| 时刻 | 精确到秒，标注时区 |
| 事件 | 发生了什么（可观测的） |
| 来源 | 谁记录的：日志 / 告警 / 当事人回忆 / 系统指标 |
| 可信度 | 硬证据（日志）/ 软证据（回忆） |

**来源与可信度两列不能省。** 当事人回忆和系统日志的权重完全不同，混在一起写就会得出错误结论。

#### 1.2 区分三种事实

| 类型 | 例 | 权重 |
|---|---|---|
| **硬证据** | 日志、监控数据、审计记录、代码提交记录 | 最高 |
| **弱证据** | 截图、口头描述、事后回忆 | 中 |
| **推断** | "应该是那时开始的" | 零，单独标注 |

#### 1.3 找"沉默的证据"

**最难也最关键的**：记录缺失的地方。

- 某段时间没有日志 → 是没发生，还是日志没打？
- 某服务没有告警 → 是没问题，还是没配告警？

**"没有记录"和"记录显示没有"是两件事。**

### 阶段二 · 假设与排他

事件溯源里的假设通常是**叙事**：几种可能的经过。

| 假设 | 支持证据 | 反对证据 | 鉴别动作 |
|---|---|---|---|
| A：先是配置变更，再引发雪崩 | 变更时间在告警前 3 分钟 | 变更前已有慢查询 | 查变更前 10 分钟的错误率 |
| B：先是流量突增 | 流量曲线在 T 时刻翻倍 | 容量余量足够 | 查同集群其他服务是否也慢 |

#### 鉴别动作：找"如果 A 成立，应该还看到什么"

这是溯源里最强的技巧。

> 如果真因是配置变更，那么在变更前后，**同一个指标的形态应该出现阶跃**。
> 如果没出现阶跃，A 大概率不成立。

**用"应该还会留下什么痕迹"来验证假设，比找支持证据有效得多。**

### 阶段三 · 根因溯源

事件溯源的根因通常不是单点，是**链条**。要写成因果链，不是一句话。

```
触发（第一张多米诺）
  → 放大（什么让它从小问题变大问题）
    → 失效（本来该拦住它的防线为什么没拦住）
      → 未发现（为什么这么久才被发现）
```

**四段都要有，缺哪段就补哪段的证据。**

| 段 | 典型问题 |
|---|---|
| 触发 | 第一次偏离正常是什么 |
| 放大 | 为什么没被局部化 |
| 失效 | 熔断/限流/重试/降级 哪个没起作用 |
| 未发现 | 监控盲区在哪 |

#### 根因判定三条件

- **可控**：有人能改变它
- **可验证**：能设计实验证伪
- **解释全部**：不能只解释一部分现象

不满足就是"原因之一"，不是根因。

### 阶段四 · 处置与防御

事故复盘的处置重点与其它场景不同：**大部分时候"止损"已经过去了，重点是"下次多久能发现"。**

| 级 | 事故场景的重点 |
|---|---|
| **① 止损** | 如果还没恢复，先恢复；如果已恢复，确认没有残留影响 |
| **② 根治** | 消除链条上的关键环节 |
| **③ 长效** | **MTTD（发现时间）和 MTTR（恢复时间）比"不再发生"更现实** |

### 一个现实主义的判断

**大部分事故无法做到"不再发生"。** 能做的是：

- 让它**更晚**发生（降低概率）
- 让它**更早**被发现（缩短 MTTD）
- 让它**更快**被恢复（缩短 MTTR）

**把防御写成"杜绝此类问题再次发生"是不专业的。** 写成"把发现时间从 40 分钟压到 5 分钟"才是可交付的。

## 三、复盘的三条纪律

1. **对事不对人。** 一旦开始追责，后续所有信息都会失真——没人会再说真话。
2. **区分"决策"和"结果"。** 当时信息下的合理决策，导致了坏结果，不该被判定为错误决策。
3. **写"如果重来"，不写"如果当初"。** 前者可执行，后者只是遗憾。

## 四、这个场景的高频错误

| 症状 | 根因 | 修法 |
|---|---|---|
| 时间线混乱 | 硬证据与回忆混写 | 分来源、标可信度 |
| 结论只有一个原因 | 没下潜到链条 | 写四段因果链 |
| 复盘变成甩锅 | 对人了 | 只讨论机制 |
| 防御写得很大 | "杜绝再次发生" | 改成可量化的 MTTD/MTTR |
| 忽略"没发现" | 只看"为什么发生" | 补第四段 |

## 五、输出片段

```markdown
## 一、时间线
| 时刻 | 事件 | 来源 | 可信度 |
|---|---|---|---|
| 10:02:11 | 发布 v2.3.1 | CI 记录 | 硬 |
| 10:05:40 | 错误率开始上升 | 监控 | 硬 |
| 10:06:00 | 首条用户投诉 | 客服 | 弱 |
| 10:45:00 | 触发告警 | 监控 | 硬 |

## 二、关键缺口
- 10:05–10:45 之间无任何告警：错误率告警阈值设为 5%，实际峰值 4.2%

## 三、因果链
- 触发：v2.3.1 引入空值未判空
- 放大：该接口被 3 个页面复用，错误率被分散到各页面，单页面未达阈值
- 失效：无自动回滚，回滚需人工判断
- 未发现：告警按接口维度而非全局维度

## 四、处置
- ① 止损：已回滚，确认无残留脏数据
- ② 修复：补判空 + 3 个用例
- ③ 长效：
  - 告警改为全局错误率（MTTD 目标：从 40min 降到 5min）
  - 灰度发布：5% → 25% → 100%，每阶段观察 10 分钟
  - 回滚脚本化（MTTR 目标：从 5min 降到 1min）
```
