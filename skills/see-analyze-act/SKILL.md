# 见·析·行

同一个事实，可以写成一段猜测，也可以写成一份诊断。差别只在结构。

```
见（Observe）   → 我看到什么，我没看到什么
析（Analyze）   → 为什么会这样，分几层
行（Act）       → 现在做什么，以后怎么不复发
```

这个框架的价值不在"分三步"——**在于每一段都强制你交代自己的边界**。

## 什么时候用

- 根据有限证据给出可执行结论（设备异常、病害诊断、数据归因、事故复盘）
- 证据不完整但必须给建议
- 需要别人复现你的判断过程

**不适合**：有唯一确定答案的计算题、纯粹的检索问答。

## 一 · 见（Observe）

四个动作，顺序不能变。

### 1. 先声明视野边界

**在说任何结论之前，先说清这次能看到什么、看不到什么。**

| 声明项 | 例 |
|---|---|
| 证据类型 | 远距离监控画面 / 近景特写 / 传感器读数 / 用户口述 |
| 分辨率极限 | 远距离画面看不到体表细节，只能判姿态 |
| 时间覆盖 | 只有单帧 / 有 3 帧序列 / 有 7 天历史 |
| 缺失项 | 没有水温数据、没有设备日志 |

**为什么先做这个**：边界一旦说清，后面所有推断都有了可解释的范围。反过来，先给结论再补边界，读的人只会记住结论。

### 2. 只提取可观测事实

写"画面里有什么"，不写"这意味着什么"。

- ✗ 「鱼群摄食积极性差」 ← 这是推断
- ✓ 「投饵后 30 秒内，鱼群未向落料点聚集，仍在网箱边缘单向巡游」 ← 这是观察

### 3. 把观察与推断分开写

格式上强制分开：

```
观察：……
推断：……（置信度：高/中/低）
无法确认：……
```

### 4. 给出前 1–3 个疑似方向

不要只给一个。**给一个等于赌，给十个等于没给。**

## 二 · 析（Analyze）

归因分三层，逐层下沉。

| 层 | 回答的问题 | 例 |
|---|---|---|
| **直接原因** | 当下这个现象由什么直接引发 | 病原体 / 部件失效 / 输入参数错 |
| **诱发条件** | 什么环境让直接原因得以发生 | 温度区间、负载峰值、操作时序 |
| **系统性原因** | 为什么这个条件长期存在 | 缺少监控、流程缺失、设计假设过时 |

**只写到"直接原因"是最常见的偷懒。** 直接原因能解释"发生了什么"，但解释不了"为什么老是发生"。

### 三条归因纪律

1. **诱因必须是你观察到或能佐证的**，不是"可能"列表。
2. **系统性原因可以留空**，但要说"本次未发现系统性因素"。
3. **不要在证据不足时给高置信度。** 低置信度是一个合法结论。

## 三 · 行（Action）

两级行动，分开写。

### 应急处理（止损）

要求：**今天就能做、有明确负责人、有完成判据。**

- ✗「加强管理」
- ✓「立即停机换备用线路；30 分钟内完成；完成后回报切换日志」

### 长效预防（固化）

要求：**改变机制，不是提醒人。**

- ✗「提醒操作员注意」
- ✓「在配置页对空值做强制校验，不填不允许提交」

**如果长效方案是"加强培训""提高意识"，说明你还没找到系统性原因。**

## 四 · 事实溯源四铁律

这四条决定了结论是"诊断"还是"编故事"。

1. **看不到的不能说。** 超出证据分辨能力的内容，直接写"无法确认"。
2. **只采信四类来源**：现场观测、系统实测数据、挂载的知识库、用户明确输入。其余一律标注为推测。
3. **标识符不得编造。** 上下文没给编号就写"当前对象"，不许自己生成一个像真的。
4. **空数据就是空数据。** 查不到就说"暂无记录"，不许用"通常""一般"填坑。

## 五 · 输出协议

```markdown
## 见 · 现象与定性
- 视野边界：……
- 观察：……
- 推断：……（置信度：中）
- 无法确认：……

## 析 · 归因
- 直接原因：……
- 诱发条件：……
- 系统性原因：……

## 行 · 处理与预防
- 应急（止损）：……
- 长效（固化）：……
```

结构化输出的意义：**让读的人能直接质疑中间某一步，而不是只能接受或否定整个结论。**

## 六、常见失败

| 症状 | 根因 |
|---|---|
| 结论很肯定但说不清依据 | 跳过了「见」的边界声明 |
| 分析很长但不落地 | 「行」只有口号，没有动作 |
| 同一个问题反复发生 | 只写到直接原因，没下沉到系统性原因 |
| 遇到没见过的情况就编 | 缺少事实溯源四铁律 |
| 每次都从头分析 | 没有把结论沉淀成可复用的鉴别点 |
