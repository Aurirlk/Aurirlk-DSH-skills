# see-analyze-act

> 本技能是 [Aurirlk DSH Skills](../../README.md) 合集的一员 · [← 返回仓库目录](../../README.md)

**中文** | [English](README.en.md)

三段式领域诊断推理：**见 · 析 · 行**。

同一个事实，可以写成一段猜测，也可以写成一份诊断。差别只在结构——而这个框架的价值不在"分三步"，**在于每一段都强制你交代自己的边界**。

## 什么时候用

根据有限证据给出可执行结论：设备异常排查、病害/故障诊断、数据异常归因、事故复盘。

**尤其适用于「证据不足但必须给建议」的场景**——这正是最容易开始编的地方。

## 三段结构

| 段 | 强制动作 | 失败长什么样 |
|---|---|---|
| **见** | 先声明视野边界，再只写可观测事实，观察与推断分开 | 结论很肯定但说不清依据 |
| **析** | 三层归因：直接原因 → 诱发条件 → 系统性原因 | 同一问题反复发生 |
| **行** | 两级行动：应急止损（今天能做）+ 长效固化（改机制） | 分析很长但不落地 |

## 「见」的四步

```
1 声明视野边界   → 能看到什么、看不到什么、缺什么数据
2 只提取事实     → 写"画面里有什么"，不写"这意味着什么"
3 观察与推断分列 → 观察：…… / 推断：……（置信度）/ 无法确认：……
4 给 1–3 个疑似方向 → 给一个等于赌，给十个等于没给
```

## 「析」的三层

| 层 | 回答什么 |
|---|---|
| 直接原因 | 当下这个现象由什么直接引发 |
| 诱发条件 | 什么环境让直接原因得以发生 |
| 系统性原因 | 为什么这个条件长期存在 |

**只写到"直接原因"是最常见的偷懒**——它解释得了"发生了什么"，解释不了"为什么老是发生"。

## 「行」的两级

- **应急**：今天就能做、有负责人、有完成判据
- **长效**：改变机制，不是提醒人

> 如果长效方案是"加强培训""提高意识"，说明你还没找到系统性原因。

## 事实溯源四铁律

1. **看不到的不能说**——超出证据分辨能力的，直接写"无法确认"
2. **只采信四类来源**：现场观测 / 系统实测数据 / 挂载知识库 / 用户明确输入
3. **标识符不得编造**——没给编号就写"当前对象"
4. **空数据就是空数据**——查不到就说暂无记录

## 输出结构

```markdown
## 见 · 现象与定性
- 视野边界 / 观察 / 推断（置信度）/ 无法确认

## 析 · 归因
- 直接原因 / 诱发条件 / 系统性原因

## 行 · 处理与预防
- 应急（止损）/ 长效（固化）
```

结构化输出的意义：**让读的人能直接质疑中间某一步，而不是只能接受或否定整个结论。**
