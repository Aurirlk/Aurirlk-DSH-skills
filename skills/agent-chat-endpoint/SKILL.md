# Agent 对话端点

一个能回答的 agent 和一个**能用的**对话产品，差四件事：

```
① 增量怎么映射  ② 什么时候算答完  ③ 历史怎么落  ④ 上下文超了怎么办
```

这四件事互相咬合。任何一件处理错，现象都会落在用户眼前，而根因往往在另一层。

## 一、增量映射：空白也是内容

### 症状

气泡里文字挤成一坨，标题、表格、分隔线全部不渲染，但 `**粗体**` 是好的。

### 根因

模型会把 `"\n"`、`" "`、`"  \n"` **单独成帧**发出来。后端用 `isBlank()` 过滤"空增量"，把这些帧全丢了 → 累积正文里一个换行都没有 → markdown 的块级规则（标题 / 表格 / 分隔线 / 列表）全部失效，只有行内语法幸存。

看起来像"markdown 只渲染了一半"，实际是**换行被吃了**。

### 规则

| 判断 | 用在哪 | 语义 |
|---|---|---|
| `isEmpty()`（只判 null / 空串） | 正文 / 思考增量下发 | 空白帧**必须下发** |
| `isBlank()`（含纯空白） | 判断"模型是否真的回答了" | 纯换行不算答案 |

**两个判断不能混用。** 用 `isBlank()` 决定下不下发 = 吃掉换行；用 `isEmpty()` 决定"有没有回答" = 空白气泡被当正常收尾。

### 前端配套

流式期间改对象要拿**响应式代理**：

```js
s.msgs.push({ text: '' })
const reply = s.msgs[s.msgs.length - 1]   // ← push 进去的是原始对象，改它不触发渲染
reply.text += chunk                        // 改代理，才会逐帧更新
```

直接改 push 进去的那个原始对象，界面会一帧不动，等某个真 ref 变化时才整体重渲染 —— 表现就是"卡几秒然后一股脑全跳出来"。

## 二、收尾语义：慢动作不许挂流尾

### 症状

回答已经显示完了，转圈还转 2-3 秒。

### 根因

为了"顺手"在流末尾多做一件事（起标题、压缩上下文、写摘要），而那件事要**再调一次模型**。
放 `completion` 之前 → 推迟收尾帧；放 `completion` 之后 → 前端见到 `completion` 就 `reader.cancel()`，根本收不到。

两头堵死。

### 规则

**额外一次模型调用，一律做成独立端点**，前端在 `onDone` 里 fire-and-forget：

```
POST /sessions/{id}/auto-title      ← 不进 SSE 流
```

配套两条：

1. **幂等闸门放后端**：标题仍等于默认值（首条提问截断）才重新生成，否则返回 `generated=false`。这样前端每轮都发也不烧 token，还顺带解决"首轮失败 → 永远没标题"。
2. **并发覆盖用乐观锁**：生成期间用户可能改名 → `renameIfUnchanged` 把原标题放进 `WHERE`，影响 0 行就保留用户改的名字。

## 三、历史落库：失败不能拖垮对话

### 四条硬规则

1. **ThreadLocal 登录态必须在 Servlet 线程取。**
   SSE 的写线程不是请求线程，`doFinally` 里取 `userId` 必然是 null → "聊完一条历史都没存"。
   在 `stream()` 进入时取好，一路传下去。

2. **落库失败绝不能让对话失败。**
   `begin` / `finish` 全包 try-catch，只记 warn。
   建表脚本没在生产跑时，表现应该是"能聊但没历史"，不是"发不出消息"。

3. **归属校验写进 SQL，不要只在 Service 判断。**
   接口暴露自增 id，只按 id 读等于"改个数字就能看别人的对话"。

   ```sql
   SELECT ... WHERE id = ? AND creator_id = ?
   ```

4. **会话懒创建 + 首帧回传真 id。**
   前端本地临时 id 靠 `session` 事件换成真 id，否则每条消息都开一个新会话。
   前端要把 `Session.key`（列表 key / 选中态）与 `Session.id`（服务端 id，0 = 未落库）分开 —— 不能拿 id 当列表 key，多个草稿会撞。

### 落库时机

`complete` / `cancel` / `error` **都落**，用 `AtomicBoolean` 保证只落一次。
取消和报错也是真实发生过的对话，丢掉就再也拼不回现场。

## 四、上下文预算：压缩不改史

### 三条规则

1. **边界用消息 id，不用"前 N 条"。**
   消息会持续追加，"最近 20 条"这种序号边界会漂移。存 `upto_message_id`，语义稳定。

2. **压缩不删、不改原消息。**
   摘要只影响"投喂给模型的那一份"。原始历史永远完整 —— 用户能翻、能引用、能重新压缩。

3. **摘要回投用 USER 角色，并明确标注"这不是新提问"。**
   不要塞 SYSTEM：不同框架里 SYSTEM 位往往已被 agent 提示词占着，再塞一条行为不一致。

### 前后端必须同源

"单条消息上限"（`PER_MESSAGE_CAP`）这类常量，**前后端只能有一个数字**。
各写一个，就会出现"界面说全进去了，模型只拿到 4000 字"。

预算档位建议做成**请求级参数**（`contextBudgetTokens`），不传则由服务端配置兜底；token 数按字符估算时要在 UI 上标"约"。

## 五、响应类型分流

同一个端点，成功回二进制、失败回 JSON 是很常见的做法（比如 TTS）。

```js
// 错：res.json() 会把音频读坏；res.blob() 会把错误信息变成放不出来的音频
const ct = res.headers.get('content-type') || ''
const data = ct.includes('application/json') ? await res.json() : await res.blob()
```

**必须按 `Content-Type` 分流。** 不能按状态码猜 —— 200 也可能回 JSON。

## 六、故障 → 判据对照表

| 现象 | 先查这里 | 典型根因 |
|---|---|---|
| 文字挤成一坨、表格不渲染 | 累积正文字符里的 `\n` 个数 | 空白增量被 `isBlank()` 过滤 |
| 卡几秒后一次性全跳出来 | 前端改的是不是代理对象 | 改了 push 前的原始对象 |
| 答完还转圈 | 流尾是否有额外模型调用 | 慢动作挂在 `completion` 前后 |
| 聊完一条历史都没有 | `userId` 在哪取的 | 在写线程 / `doFinally` 取 ThreadLocal |
| 聊天能发但历史为空 | 生产是否跑了建表脚本 | 落库降级为 warn（设计如此） |
| 越权能看到别人的会话 | 查询是否带 `creator_id` | 只在 Service 判，SQL 没带 |
| 压缩后开始胡说 / 丢最近几轮 | 边界写法 | 用"前 N 条"而非 `upto_message_id` |
| 音频放不出来但内容是报错 | 前端解析方式 | 没按 `Content-Type` 分流 |

## 七、自检

- [ ] 空白增量会下发；"是否回答"用另一个判断
- [ ] 流尾没有额外模型调用；慢动作是独立端点
- [ ] 独立端点有幂等闸门，重复调用不烧 token
- [ ] `userId` 在请求线程取
- [ ] 落库全 try-catch，失败不影响对话
- [ ] 所有按 id 的读写都带 `creator_id`
- [ ] `complete` / `cancel` / `error` 都落库，且只落一次
- [ ] 压缩边界是消息 id；原消息未被修改
- [ ] 上限常量前后端同源
- [ ] 混合响应类型按 `Content-Type` 分流
