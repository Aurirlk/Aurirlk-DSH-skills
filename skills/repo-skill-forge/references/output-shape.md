# 生成物的结构：每一册治什么病

为什么切成这些分册，而不是一本大文档：**人查东西是按问题查的，不是按目录查的。**
"接口在哪"和"这张表谁在写"是两个不相关的问题，塞在同一页只会互相干扰。

## 00-overview：三十秒建立坐标系

**回答的问题**：这仓库多大、用什么写的、怎么跑起来。

**必须有的**：规模数字（文件/行数/测试占比）、语言分布、技术栈（从依赖推）、构建与验证命令、剩余分册的导读。

**容易写坏的**：

- 技术栈靠猜。"这是 Spring Boot 项目"要能从 `pom.xml` 的依赖里指出来，不能从仓库名看出。
- 命令没有出处。`mvn test` 和 `./mvnw -q test` 都可能对，但只有一个是真的——写上你是从哪读到的。
- 把 overview 写成 README 复制品。README 是给使用者看的，overview 是给改代码的人看的。

## 01-modules：谁依赖谁，实际流向是什么

**回答的问题**：有几个模块、各多大、谁能依赖谁。

**这一节最有价值的不是模块表，是"清单声明 vs 代码实际"的对照。** 构建文件说 A 依赖 B，代码里可能 B 反过来 import 了 A——那就是循环依赖的起点，而且构建工具不会报。

**容易写坏的**：

- 只抄构建文件的 modules 列表。那张表在 `pom.xml` 里本来就有，抄一遍没有信息增量。
- 不提跨模块 import 次数。次数才是"耦合有多紧"的度量。

## 02-entrypoints：进程起来之后发生了什么

**回答的问题**：从哪个类/文件开始读，第一跳调了什么。

**必须有的**：入口位置（`file:line`）、入口类型（Spring Boot / main / 前端挂载 / CLI）、以及用 `query.mjs callees` 拉出来的第一跳。

**这一节的 TODO（E1）是最值得认真写的**：新人卡住的地方几乎都在这里——知道入口在哪，但不知道起来之后装配了什么。

## 03-api：对外契约的完整清单

**回答的问题**：有哪些端点、谁处理的、路径长什么样。

**必须有的**：方法、完整路径（含常量前缀解析后的结果）、处理器类名#方法、`file:line`。

**容易写坏的**：

- 路径丢了前缀。`@RequestMapping(PATH_CONSTANT)` 这种写法，不解析常量就会得到 `/config` 而不是 `/api/xxx/config`。生成器已经做了两阶段常量解析，但**解析失败的会保留成 `<NAME>`，这部分绝对不能当契约用**。
- 把 `@Deprecated` 的、注释掉的端点也算进来。扫描器不判断语义，这一步靠人。
- 前端仓库没有 HTTP 端点时，这一册应该换成"路由 → 页面组件"的映射，而不是留空。

## 04-datamodel：类名和表名到底怎么对

**回答的问题**：这个 `XxxPO` 对应哪张表、谁在写它。

**必须有的**：模型名、表名、来源（`@TableName` / `@Table` / DDL / 推断）、`file:line`。

**关键纪律**：**推断必须标出来。** `@TableName("agent_run")` 是事实；把 `RunRecordPO` 转成 `run_record_po` 是推断。两者混在一起写，出错时没人知道该信哪条。

## 05-config：键名可以给，值绝对不行

**回答的问题**：这个项目要配哪些东西、哪些是敏感的。

**必须有的**：键名、类型（env / yaml / properties / `@ConfigurationProperties`）、出现位置、是否疑似敏感。

**绝对禁止**：任何值。哪怕是 `localhost:3306`。配置值里混着密码和 token，一次误贴就是安全事故，而且事后很难判断泄了哪些。

**TODO（C1）的价值**：标出"少一个就起不来"的必填项。这个信息只能从代码里有没有兜底看出来，键名看不出来。

## 06-conventions：这个仓库实际长什么样

**回答的问题**：命名习惯是什么、有没有格式门禁、欠了多少债。

**必须有的**：类名后缀分布、检查/格式化配置、测试比、`any`/`console`/`TODO`/`FIXME`/`HACK` 计数。

**纪律**：这一节只写**统计事实**，不写规范条文。团队规范在团队文档里；这里回答"代码实际怎么写"。

`HACK` 要单独强调：它带着"暂时绕过"的隐含前提，前提失效时静默出错，比 `TODO` 危险得多。

## 07-landmines：改之前必须知道的

**回答的问题**：哪个文件改了最危险、哪个模块没测试。

**必须有的**：最大文件（附符号数）、扇入最高的文件、无测试模块、扫描器自己的边界。

**为什么单列一册**：因为这些信息在别的分册里是"一条数据"，放在这里才是"一句警告"。人不会从模块表里自己推出"这个文件 6000 行所以别乱动"。

## 10-module-*：每模块一册

**回答的问题**：我要动这个模块，得先知道什么。

**必须有的**：规模、依赖、目录角色、文件清单（全量或明确截断）、主要符号、本模块端点/模型、测试情况、三个 TODO（职责 / 典型流转 / 特有坑）。

**为什么每模块一册而不是一节**：大仓库的模块册会到几百行，塞进一个文件后没人会滚到第三个模块。分开还有个好处：改 A 模块的人只需要读 A 的那册。

**目录角色**是个小设计但很有用：`views/` 是页面、`components/` 是组件、`service/api` 是接口层。它让"这堆文件是干什么的"一眼可见，而不是靠路径猜。

## AGENT-CHECKLIST：不许忘的收尾

**回答的问题**：还有哪些必须人写、写在哪、写完怎么验。

**必须有的**：编号、位置、要写什么、合计数量。

编号不是装饰：它让"补完了没有"变成可数的事实，而不是"差不多写完了"。
