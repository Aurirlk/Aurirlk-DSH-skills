# 交付真实性审查

有三种东西长得像功能，但一碰就碎：

| 形态 | 表面 | 真相 |
|---|---|---|
| **假数据** | 页面有数据、图表有曲线 | 数据是硬编码的 / 随机生成的 |
| **假实现** | 类在、接口实现类在、配置项在 | 方法是 `return null` / `TODO` / 占位返回 |
| **假完成** | 文档写"已集成"、清单打勾 | 代码里没有，或者写了但没人调用 |

三种的共同点：**看起来完成，实际不解决问题**。而它们都会在演示里过关 —— 这是它们能活下来的原因。

## 为什么必须较真

一旦允许"先塞点假数据让界面好看"，后面所有判断都建立在沙上：

- 联调时以为是对方的问题
- 上线后第一真实请求就崩，而排查方向被假数据带偏
- 文档与代码脱节，下一个人花两天重新发现"这是假的"

**这不是效率问题，是信用问题。** 一次被认定为"糊弄"，后面每句话都要被怀疑。

## 一、假数据的识别

### 症状

- 数据"太完美"：全是整数、全在合理区间、时间戳连续无空隙
- 换了环境、清了库，页面依然有数据
- 接口返回的字段名与真实表结构对不上
- 代码里出现 `mockList`、`fakeData`、`demoRows`、`sampleData`、`// 示例数据`

### 判据

**问一句："这条数据是谁写进去的？"**

答不上来 = 假数据。真数据的答案永远是：某张表、某个接口、某次上传、某个任务写入。

### 正确做法

看不到数据时，**补齐真实能力**，而不是伪造：

| 场景 | ✗ 错误 | ✓ 正确 |
|---|---|---|
| 页面没有数据可选 | 塞几行 mock 让下拉能选 | 加"上传本地文件"入口，复用真实上传接口拿真实 URL |
| 分析结果为空 | 造一份假结果展示 | 明确显示"无数据" + 告诉用户怎么产生数据 |
| 第三方服务没配 | 返回假响应假装成功 | 返回明确错误：未配置 / 未授权 |

**「让截图好看」不是需求。** 用户要的是这个功能真能解决问题。

## 二、假实现的识别：两类典型形态

### 形态 A：「迁了骨架没接电」

代码完整、结构正确、甚至单元测试都有 —— 但**全仓零引用**。

真实案例：一套图编排（358 行，含中断/恢复）+ 7 个节点，代码在、注释全、但没有任何地方调用它。更糟的是里面三个节点是假的：

- `SqlExecuteNode` 返回硬编码的假结果
- `SqlGenerateNode` 把用户输入直接当 SQL
- 意图识别靠关键词匹配

**"代码在" ≠ "功能在"。** 而且这种假货最危险：评审时看到类和方法都在，很容易就过了。

**判据：全仓 grep 这个 public 类/方法/字段的调用点。零调用者 = 没接入。**

### 形态 B：「接入但没水源」

链路后端全写好了，前端**从来不供给**这个参数。

真实案例：页面上下文补参（`datasourceId` / `tableName`）三个工具都登记了、默认值处理也写了，但前端三个页面只上报 `agentId`，`datasourceId` 全站零埋点 → 补参逻辑永远不会触发。而提示词已经向模型承诺"可以省略，会沿用页面对象"。

这类 bug 的特点：

- 每个文件单看都对
- 端到端永远走不到那条分支
- 不报错，只是"功能时好时坏"或"一直没生效"

**判据：从用户动作出发走一遍全链路，看每个参数的最初写入点在哪。找不到写入点 = 水源缺失。**

### 形态 C：占位实现被写进文档

`MinioStorageService` 类存在、接口对、方法签名对，方法体是 `throw new UnsupportedOperationException()`，而 README 里写"对象存储已集成"。

**判据：所有 `UnsupportedOperationException` / `TODO` / `return null` / `return Collections.emptyList()` 的实现类，逐个对照文档。**

## 三、假完成的识别

文档/清单说"已完成"，需要三种证据才认：

| 证据 | 强度 | 怎么看 |
|---|---|---|
| **代码存在** | 最弱 | 有空实现也算存在 |
| **有调用者** | 中 | 全仓 grep，且调用链能走到用户动作 |
| **跑通过** | 强 | 有真实请求/响应、日志、截图、测试输出 |

**三者不全，就不能打勾。** 只写"代码已实现"的，标成"已实现未验证"。

### 状态该怎么写

不要二元的"完成/未完成"。用四档：

| 状态 | 含义 | 交付里怎么写 |
|---|---|---|
| ✅ 已验证 | 真实链路跑通，有证据 | 附证据（截图 / 响应 / 日志片段） |
| 🟠 已实现未验证 | 代码在、有调用者，没跑过端到端 | 说明缺哪一步验证 |
| 🔴 未实现 | 只有接口 / 空实现 | 说明阻塞点 |
| ⚪ 不适用 | 评估后决定不做 | 说明为什么不做 |

「已实现未验证」这一档是这套体系的关键 —— 它让"我没骗你，但我也不敢打勾"变成一种**体面的状态**。
没有这一档，人只能被迫在"撒谎"和"承认什么都没做"之间选。

## 四、交付前审查流程

```
1. 列功能清单（以用户能做的动作为单位，不是以类为单位）
2. 每条找三样证据：入口 / 调用链 / 真实输出
3. 缺证据的，降级状态，写明缺什么
4. 扫三类假货（mock 关键字 / 零引用 public 方法 / 空实现）
5. 把"假"改成"真"或改成"如实标注"
```

### 扫描清单（可直接跑）

```bash
# 假数据
grep -rniE "mock|fake|dummy|sampleData|demoRows|示例数据" --include=*.{java,ts,vue,py} .

# 空实现
grep -rn "UnsupportedOperationException\|TODO\|FIXME" --include=*.java .

# 硬编码返回值（人工看，别自动改）
grep -rn "return Collections.emptyList()\|return null;" --include=*.java .
```

## 五、被质疑时的正确反应

用户说"这是假的吧"，**不要辩解，立刻自查并给结论**。

正确的话术结构：

1. 承认具体哪部分是假的（不要含糊说"部分内容"）
2. 解释它为什么在那儿（是临时占位？从没接？）
3. 给两条路：现在补真链路 / 明确标为未实现
4. 不要顺手把责任推给"时间不够"或"需求没说清"

**信任是单次消耗品。** 一次糊弄，后面所有"已完成"都要打折。

## 六、自检

- [ ] 每个"能用的功能"都能说出数据来源（哪张表 / 哪个接口 / 哪次写入）
- [ ] 新写的 public 类 / 方法全仓有调用者
- [ ] 没有为了演示而硬编码的返回值
- [ ] 空实现没有被写进"已完成"
- [ ] 文档里的"已集成"都有三样证据
- [ ] 未完成项用了四档状态，不是二元打勾
- [ ] 没有"看得见调不通"的能力（工具注册了但没配置 / 提示词承诺了但没实现）
