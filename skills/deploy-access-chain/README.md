# deploy-access-chain

> 本技能是 [Aurirlk DSH Skills](../../README.md) 合集的一员 · [← 返回仓库目录](../../README.md)

**中文** | [English](README.en.md)

改了文件、重新构建、覆盖上去 —— 刷新，还是旧的。

这是运维里最消耗人的一类问题：**你每一步都是对的，但结果没变。** 于是你反复覆盖、清缓存、重启，每次都"好像生效了"，下次刷新又回到旧版。

根本原因通常只有一个：**你改的那份文件，不在请求链路上。**

## 什么时候用

- 重新构建并覆盖了前端产物，浏览器里还是旧版本
- 不确定请求是打到本机 nginx、前置负载均衡、CDN，还是另一个实例
- 要判断某份配置到底在不在请求链路上
- 已经试过"清缓存 / 加 `?bust=` / reload nginx"，都没用

## 第一件事不是覆盖

而是**证明请求真正落在哪份文件上**。

五层证据链，由便宜到贵：

```
1 构建指纹   → 资源哈希 / buildTime，全盘反查
2 响应头     → Last-Modified、Server、Via、X-Cache、自定义 add_header
3 访问日志   → curl 前后对比，有无新增 ← 最一锤定音
4 监听端口   → ss -lntp、/proc/net/tcp、iptables / nft、netns
5 DNS 两路   → getent + curl --resolve（127.0.0.1 和私网 IP 都要测）
```

**第 3 层能省掉几小时的猜测**：公网请求在本机 `access.log` 里有新增 → 流量确实过这里；零新增 → 这条请求根本不经过这台机器，覆盖本机文件永远不会生效。

## 结论纪律（这个技能真正的核心）

| 类型 | 要求 |
|---|---|
| 硬事实 | 附命令与原样输出 |
| 推断 | **必须写：什么结果能推翻它** |
| 已撤回 | 明确撤回，保留仍成立的硬事实 |

没有证伪条件的推断会自我加固 —— 每看到一个不符的现象，都能解释成"另一种情况"。

## 五个坑

- **不存在的 JS 也返回 200**：SPA `try_files` 兜底，状态码不能判断文件是否存在
- **`?bust=` 无效不排除 CDN**：CDN 常忽略 URL 参数，也不理会客户端 `no-cache`
- **`nginx -T | grep 目录名` 为空不代表没读**：隐式 root + 通配 location
- **配置可能不在 conf 里**：nginxWebUI 这类面板存 sqlite 再下发，还支持纳管远程节点
- **多行命令贴到终端会被吃掉**：续行符 `\` 丢失 + `2>/dev/null` 吞错 = 静默返回空

## ⚠️ 边界

- 只做**只读取证**。确认链路之前，不建议覆盖、删除、reload 任何生产文件
- 面向 nginx / CDN / LB 组合环境；其它 web server 判据相通，命令需替换
- 需要装包（`tcpdump` 等）时先问：有没有不装包就能得到同样结论的命令

## 安装

```powershell

pnpm add github:Aurirlk/Aurirlk-DSH-skills
```

## 平台

Linux 服务器为主（nginx / ss / iptables / nft）。命令以只读为主，适合让有权限的人照着跑。
