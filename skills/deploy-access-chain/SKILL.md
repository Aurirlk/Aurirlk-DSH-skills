# 改了文件，线上没变

这是运维里最消耗人的一类问题：**你做的每一步都是对的，但结果没变**。于是你开始重复覆盖、清缓存、重启 —— 每一次都"看起来生效了"，下一次刷新又回到旧版。

根本原因通常只有一个：**你改的那份文件，不在请求链路上。**

所以第一件事不是覆盖，是**证明请求真正落在哪份文件上**。

## 一、结论纪律：硬事实与推断分开写

这类问题最容易出错的不是命令，是**推理**。一条推断被当成事实传下去，后面所有动作都白做。

| 类型 | 例子 | 要求 |
|---|---|---|
| **硬事实** | 「本机 `ss -lntp` 无 443 监听」 | 附命令与原样输出 |
| **推断** | 「所以 443 由前置层提供」 | 必须写：**什么结果能推翻它** |
| **已撤回** | 「我先前说'不是同一台机器'，错了」 | 明确撤回，并保留仍成立的硬事实 |

**给推断留一个证伪条件**，是这套方法唯一能防止"越查越偏"的机制。
没有证伪条件的推断会自我加固：每看到一个不符的现象，都能解释成"另一种情况"。

### 被推翻时怎么说

不要悄悄改口。写清三行：

```
原推断：X
推翻依据：<哪条命令、什么输出>
仍成立：<那些不依赖 X 的硬事实>
```

用户不会因为你改口而少信任你，但会因为你不说而不再信任你。

## 二、五层证据链（由便宜到贵）

### 第 1 层：指纹

找一个**只属于这一版**的标记，全盘反查它出现在哪。

- 前端构建：`<meta name="buildTime" content="...">`、资源哈希 `index-BmcaW9Lm.js`
- 后端：jar 的 `MANIFEST` 时间、版本号常量、启动日志里的 `git.commit`

```bash
grep -rl "index-BmcaW9Lm" /data 2>/dev/null
find / -name "index-liTOXt0z.js" 2>/dev/null
```

**先拿公网返回的指纹**（`curl` 页面里的哈希），再拿磁盘上的，两者不一致就说明"HTTP 返回的不是这份文件"。

> 注意：**文件大小、状态码都不能当指纹**。SPA 的两个版本 `index.html` 可能都恰好 607 字节。

### 第 2 层：响应头

```bash
curl -sS -D - -o /dev/null https://your.site/path/index.html
```

| 头 | 说明什么 |
|---|---|
| `Last-Modified` / `ETag` | 服务端认为的文件时间 —— 和磁盘 `mtime` 对比 |
| `Server` | 哪个 web server（版本可能暴露是哪个实例） |
| `Via` / `X-Cache` / `Age` | 中间有缓存层 |
| `X-Powered-By` | 可能是应用直接返回，不是静态文件 |
| 自定义 `add_header`（如 COOP/COEP） | **反查配置文件的捷径** —— 比 grep 目录名可靠 |

**捷径**：配置里显式 `add_header` 的头，是这份配置独有的指纹。全盘 grep 这个头名，比 grep 目录名更容易命中（配置可能用变量拼 root，不含目录字面量）。

### 第 3 层：访问日志关联（最一锤定音）

```bash
# 记录当前末行
tail -1 /var/log/nginx/access.log
# 发一次公网请求
curl -sS -o /dev/null https://your.site/path/index.html
# 再看日志
tail -3 /var/log/nginx/access.log
```

- **有新增** → 流量确实过这台 nginx，继续在它的配置里找 root。
- **没有新增** → **这条请求根本不经过这里**。443 由别处提供（云 LB、CDN、另一实例、容器网络）。此时在本机覆盖文件**永远不会生效**。

这一个实验能省掉几小时的猜测。**先做它。**

### 第 4 层：监听端口与网络命名空间

```bash
ss -lntp                      # 谁在听哪些端口
cat /proc/net/tcp | head      # 十六进制端口：443 = 01BB
iptables -t nat -S            # DNAT？（为空不排除，可能用 nftables）
nft list ruleset
```

**三个必须知道的判读陷阱：**

1. **公网 IP 不在网卡上是正常的。** 云主机 EIP 是 1:1 NAT，`ip -4 addr` 只看到私网 IP。**不能**据此说"不是这台机器"。
2. **`iptables -t nat -S` 为空不代表没有 DNAT。** 可能走 nftables。
3. **`curl --resolve` 要测两个地址**：`127.0.0.1` 和**私网 IP**。EIP 1:1 NAT 下报文目的地址是私网 IP，只测 loopback 会漏掉绑在网卡上的监听者。

### 第 5 层：DNS 与两路对比

```bash
getent hosts your.site
curl -vk --resolve your.site:443:127.0.0.1   https://your.site/path
curl -vk --resolve your.site:443:10.0.0.12   https://your.site/path   # 私网 IP
curl -s  http://127.0.0.1/path -H "Host: your.site"   # 走本机 80，带正确 Host
```

- 前面两路都 `Connection refused` → 本机这个 netns 没有 443。
- 本机 80 带 Host 返回 403 → 可能是 `deny` 规则，或 worker 用户无读权限（先看目录权限 `755`/`644`，再看配置）。
- 本机 80 返回新哈希、公网返回旧哈希 → 中间有缓存层或回源到了别处。

## 三、五个坑

| 坑 | 真相 |
|---|---|
| 「不存在的 JS 也返回 200」 | SPA 的 `try_files ... /index.html` 兜底：任何 404 路径都回 index.html。**状态码不能用来判断静态文件是否存在**，要看 body 长度/内容 |
| 「加了 `?bust=` 还是旧的」 | 不能排除 CDN —— CDN 常忽略 URL 参数，也不理会客户端的 `no-cache` |
| 「`nginx -T \| grep 目录名` 是空的」 | 配置可能用隐式 `root` + 通配 `location`，不含该字面量。`nginx -T` 也只 dump **本机磁盘那一份** |
| 「配置不在 conf 里，那就不存在」 | nginxWebUI 这类面板把配置存自己的库（sqlite）再下发，还支持纳管**远程节点**。要看面板的节点列表 |
| 「多行命令贴过去语法错误但没报错」 | 终端（FinalShell 等）会吃掉续行符 `\` 和转义括号，`2>/dev/null` 又把错误吞了 → 静默返回空，被当成"全盘没有" |

**最后一条的解法**：给用户的服务器命令**一律单行**、无反斜杠续行、无转义括号。

## 四、真实案例：三次被推翻

一个前端发版后线上始终返回旧包的案例，中间撤回过三条推断 —— 记下来是因为**每一条错得都很有代表性**：

| 错误推断 | 依据 | 为什么错 |
|---|---|---|
| 「本机无 443 ⇒ 前端在别的机器/CLB 后面」 | `ss -lntp` 无 443 | 机器可以是同一台，但 443 不由**这个 nginx 实例**提供（可能是容器、另一个 netns、入口层回源） |
| 「`?bust=` + `no-cache` 无效 ⇒ 排除 CDN」 | 两次请求都返回旧哈希 | CDN 常忽略 URL 参数，不理会客户端 `no-cache` |
| 「`nginx -T` 里没有目录名 ⇒ 配置不读该目录」 | grep 空 | 隐式 root + 通配 location；且 `-T` 只 dump 本机那份 |

**最终一锤定音的是访问日志关联**：公网请求前后，本机 `access.log` 零新增 → 请求不经过本机 nginx → 本机覆盖 dist 无效。

硬事实始终是那几条，推断换了好几轮。**把这两者分开写，是唯一能让人跟得上你思路的办法。**

## 五、收尾

1. **确认入口层的真实静态目录**，再发版。不要在未确认前反复覆盖（会把备份目录堆满，也会让"哪份是新的"彻底混乱）。
2. **保留备份目录**，但明确标注时间，不要删到只剩一份。
3. **把最终口径写进运维文档**，包括"哪些说法被撤回过"。下一个接手的人不该重走这一遍。
4. 如果定位需要装包（`tcpdump` 之类），先问：**有没有不装包就能拿到同样结论的命令？** —— 访问日志关联、响应头、指纹反查通常就够了。

## 六、自检

- [ ] 先做了**访问日志关联**，确认请求是否经过这台机器
- [ ] 拿到了公网返回的**构建指纹**，与磁盘上的对比过
- [ ] 没有用状态码判断静态文件是否存在
- [ ] `--resolve` 测了 `127.0.0.1` **和**私网 IP
- [ ] 没有把"公网 IP 不在网卡上"当成"不是这台机器"
- [ ] `iptables -t nat -S` 为空时，也查了 nftables
- [ ] 检查过 nginxWebUI / 面板管的**远程节点**与其它 netns
- [ ] 给用户的命令是单行、无续行符
- [ ] 结论里硬事实与推断分开，每条推断写了证伪条件
- [ ] 撤回过的说法在文档里留了记录
