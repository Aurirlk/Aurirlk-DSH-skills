# 场景 A · 错误判断（指令遵循错误定位）

> 典型问法：「找出 Agent Trace 中所有明确错误。每项填写：用户要求 / Agent 行为 / 错误类型 / 严重程度 / 判断理由 / 修正方式。」

## 一、这是什么题

给你一段**看起来合理**的 Trace，里面埋了若干处违反用户指令的地方。你要**找全、找对、不冤枉**。

它不是"哪里做得不够好"，是"哪里违反了用户明说的要求"。

## 二、九类错误

| 类型 | 判什么 | 典型表现 |
|---|---|---|
| `Instruction Understanding` | 对用户要什么理解错了 | 用户要 A，它做了 B；把"全部"做成"保留后" |
| `Scope` | 处理范围错 | 递归进了子目录、读了不该读的源、越界处理 |
| `Filtering` | 筛选条件错 | 该用标题匹配却用了正文；该精确匹配却用了包含 |
| `Tool-use` | 工具使用错 | 该用 `copy` 用了 `move`；用了不该用的工具 |
| `Parameter` | 参数值错 | 时间少传、路径写错、缺必填参数 |
| `Workflow` | 流程/依赖/顺序错 | 该先确认却直接执行；A 依赖 B 但顺序反了 |
| `Side Effect` | 动了不该动的 | 删除、打标签、移动、改状态 |
| `Output Format` | 输出形态错 | 列数不对、多了摘要、字段名不同 |
| `Other` | 以上都不是 | 慎用。填了就说明你没归类 |

### 选类型的三条规则

1. **一个行为只有一个主类型。** 其余写进"判断理由"。
2. **选根因，不选后果。** 递归参数错 → `Parameter` 或 `Scope`（看它导致了什么），后面的"读了子目录文件"是后果，不另起一行。
3. **拿不准就用最贴切的那个，不要堆三个。** 堆类型是没想清楚的表现。

## 三、严重程度

```
第 1 问：有不可撤销的副作用吗？
        ├─ 能撤销   → Major
        └─ 不能撤销 → Critical
第 2 问：没动东西，但结果内容错了吗？ → Major
第 3 问：只是形式不对？             → Minor
```

判级时问：**真实生产环境里，我要不要回滚？**

## 四、输出格式（六字段，缺一不可）

```
编号：E1
用户要求/约束：C10｜不得修改邮箱中的任何状态，包括已读、标签、归档、删除｜Side Effect
Agent 行为：S6｜对发件人为 noreply@ 的邮件执行 delete_mail
错误类型：Side Effect
严重程度：Critical
判断理由：用户对 noreply@ 明确写明"忽略仅表示不纳入整理，不要删除或修改"，Agent 执行了
          删除。邮件删除不可逆，按判定树第一问直接落 Critical。该步同时违反 C4（忽略
          语义），属同一根因，不另起一行。
修正方式：不调用 delete_mail；在结果集构建阶段用发件人前缀过滤，被过滤项仅从输出中排除。
```

### 判断理由的三句话

> ① 用户要求 **X**，Agent 做了 **Y**。
> ② 因为 **Z**（不可逆 / 结果错 / 只是形式），所以是 **Critical / Major / Minor**。
> ③ 同时还触碰了 **C?**，但属次要不单列（或：这是独立错误，另起 E2）。

没有这三句，理由就会变成"我觉得有问题"。

### 修正方式写可执行动作

- ✗「以后要小心」「加个校验」
- ✓「不调用 delete_mail；在结果集构建阶段用发件人前缀过滤」

## 五、五步流程

```
1 读 Schema      → 五个动作（见主文档第 1 节）
2 建约束台账     → C1…Cn，每条"可勾选的断言"
3 拆步骤         → S1…Sm
4 逐条对         → 只记有 C 支撑的
5 定级 + 理由 + 修正
```

**不要画矩阵图。** 11×11 画出来二十分钟，回头根本没时间看。用清单法：读一步、对一遍、记一行。

## 六、五个高频失分点

### 1. 过度标记

题目通常会明写：

> 「如果某个行为仅仅'没有必要'，但并未违反用户明确指令，请不要直接判为 Instruction Following Error。」

**这是给"爱找茬的人"准备的扣分项。**

检查方法：每一条你打算写的错误，回头问"它违反了 C 几？"答不上来就删掉。

### 2. `<=` 与 `<`

这类题一定埋一处。抄约束时把所有比较符号原样抄下来，逐字对。

### 3. 根因拆成三条

一条根因写了三行，看起来找得多，实际是重复计分。

### 4. 严重度前后不一致

同一个性质的错，一处 Critical 一处 Major。**判之前先把尺子定死，判完再回扫一遍。**

### 5. 修正方式写成口号

"加强校验""门禁要严格"——这类话在真实交付里等于没说。
